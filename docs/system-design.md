# Personal Finance Tracker — End-to-End System Design

## Context

Prathik wants a beautiful, structured personal dashboard over his finances (credit cards, bank balances, loans, subscriptions, income, and — later — domestic/international stock investments). Data currently lives in a Google Sheet and will keep being entered manually into Sheets. An earlier pass at this sheet (Apps Script + native formulas) accumulated real problems: Apps Script overwriting cells without validation, broken/incomplete rollup formulas, no unified net-worth view, and messy investment-position formulas (confirmed by inspecting the live sheet).

Rather than rebuilding that sheet tab-for-tab, the ask now is to design the **whole system** — data model, storage, backend, frontend, deployment — end to end, then implement it piece by piece. Key decisions already made in conversation:
- **Stack**: Next.js app + Google Sheets API via a **service account** (not OAuth) — simplest, no expiring credentials, fits single-user use.
- **Version control**: `jj` (no colocated `.git`), documented in [CLAUDE.md](../CLAUDE.md).
- **Secrets**: never committed — enforced via [.gitignore](../.gitignore) + the Secrets Handling rule in CLAUDE.md.
- **Currency**: INR base; international investment holdings convert to INR (investments are deferred, see below).
- **Hosting**: undecided — build and run locally first (`npm run dev`), revisit hosting later. Nothing in this design should assume a specific host.
- **Data freshness**: cached reads with a manual "Refresh" action (not always-live, not a separate cache-invalidation system to hand-roll) — this maps directly onto Next.js's built-in data cache + `revalidateTag`.
- **Write-back**: the data-access layer must support full CRUD from day one, even though the UI may expose editing incrementally, page by page. **Explicit goal, stated directly by Prathik**: once a page ships, adding new data for that entity happens entirely through the app — master/definition data (a new Card, Account, Subscription, Loan, IncomeSource, FixedDeposit) included, not just log-tab entries. The point of building this app is to stop needing to open the Sheet by hand to add anything; the Sheet stays the storage layer, editable directly only as a fallback, not as the normal way to add data.
- **Layout**: an overview page plus a dedicated page per category.
- **Investments**: the old sheet's investment tabs were WIP and messy (leftover array-formula artifacts, duplicate/negative-quantity rows in `Positions IND`) — but per Prathik's request, investments are a first-class part of *this* design, not an afterthought. They still get built in their own implementation phase (see roadmap), but the domain model, storage shape, and aggregation approach are designed now, alongside everything else.

## Domain model

Normalizing rather than copying the old sheet 1:1. **Update, superseding the paragraph this replaces**: `Loan` was originally designed to unify Debt Book (borrowed) and Lending Book (lent) into one entity with a `direction` field. Prathik has since scoped `Loans` down to just personal loans borrowed from a bank — no lending-to-others tracking in the Loans entity; money he lends has its own tabs, see "Lent out" below — so `direction` is dropped entirely, and the field for who the loan is with is `lenderName` (not the direction-agnostic `counterpartyName`). The full amortization-schedule design (confirmed: true reducing-balance EMI, predefined due-date schedule, auto-generated at loan creation) still stands — only the borrowed/lent unification is gone.

Entities:
- **Account** (bank account: name, bank, accountType: savings/current, purpose: spending/investment/emergencyFund/loanPayments, startDate, `status: active | inactive`) → has many **BalanceSnapshot** (accountId, date, balance — a single point-in-time number).

  **Accounts columns added for the page (#160, decisions 4, 9, 12 of `docs/design/accounts.md`)**: an optional `color` (one of the shared palette, `COLORS`; a row without one shows its purpose's colour) and an optional `last4` (text, so a leading zero survives; never the full number) on the end of the tab, and `startDate` typed as Date. All three went in through the dev `sheet-columns` route (`/api/dev/sheet-columns?tab=Accounts`), which now also types a column that has no type at all. Closing an account is not a new status: it is a ₹0 balance on the day plus `Inactive`, shown as Closed.

  **Fix vs the old sheet**: `Monthly Bank Balance` stored both an Opening Balance and a Closing Balance per month, but Opening should always equal the previous month's Closing in a correct ledger — storing both is the same class of bug as everything else fixed here (a derivable value stored as if it were independent raw data, free to drift out of sync). `BalanceSnapshot` stores one balance per date; month-over-month change is computed in `lib/aggregate/accounts.ts` as `balance(t) − balance(t−1)`. `purpose` is carried over from the old sheet (e.g. distinguishing a spending account from an emergency fund) as a display/grouping field — it doesn't change net-worth math, every account's balance counts regardless of purpose.
- **Card** (credit card: name, alias, issuer, `cardType: Reward-Points | Cashback`, creditLimit, `statementDay` (1–31) / `dueDayBuffer` (days after the statement), `status: active | inactive | closed`, last4, color, optional `defaultPaidFromAccountId`; the schedule was two full anchor dates until #75) → has many **Statement** (statementDate, dueDate, totalAmountDue, minimumAmountDue, status: pending/paid, amountPaid, `accountId`/`cardId` (at most one set — see the revised cross-cutting principle below), `paidDate` — renamed from an earlier "processedDate" for consistency with `LoanInstallment`'s `dueDate`/`paidDate`, since they mean the same thing). Late fees/interest need no separate field — they simply show up baked into the following month's `totalAmountDue`. The statement day and buffer let the Overview anticipate an upcoming statement before it's been logged (`lib/aggregate/cardSchedule.ts`); utilization (outstanding ÷ creditLimit) is computed in `lib/aggregate`, not stored. The old sheet's separate "Partial Payment" column tracked over/under-payment vs the billed amount — real intent, confirmed by a real row where it was used for an overpayment — but it always duplicated `amountPaid` itself (same value in both columns); the variance it's meant to flag is just `amountPaid − totalAmountDue` (positive = overpaid, negative = underpaid), so it's computed in `lib/aggregate/cards.ts` from `amountPaid` alone rather than stored as a second raw column.
- **Subscription** (name, alias, category, amount, billingCycle, `billingAnchorDate`, startDate, `status: active | paused | cancelled`, `endDate`, `defaultPaidFromAccountId` / `defaultPaidFromCardId`, `resumedOn`, `color`: one of `COLORS` (all 36), picked freely, with the category's colour as the fallback for a row that has none) → has many **SubscriptionPayment** (subscriptionId, paymentDate, amount, `status: pending | paid | skipped`, `paidFromAccountId` / `paidFromCardId`).

  **Added in #124 (decided with Prathik 2026-10-21):**
  - **Where it's usually charged:** `defaultPaidFromAccountId` or `defaultPaidFromCardId`, at most one, following the payment-source principle below. New payments start from it.
  - **Cancelled:** a third status, with an optional cancelled-on `endDate`. A cancelled subscription keeps its payments. Paused and cancelled ones are left out of every total.
  - **`category` is a fixed list** (`SUBSCRIPTION_CATEGORIES`), each with a colour on the page: Streaming, Music, Software, Cloud-Storage, Fitness, Food, Shopping, News, Utilities, Other. The tab's dropdown holds exactly these.
  - **Card-charged subscriptions count once, by context.** The Subscriptions page counts every payment, since that's what subscriptions cost. A total of everything you'll pay counts a card-charged one only inside its card's statement. So the Overview's monthly obligations adds `monthlySpendOffCards` (active subscriptions not charged to a card, including ones with no charged-to set), not the full monthly total. One charged to a card that's no longer active (or no longer exists) is counted there too, since the Overview only adds active cards' bills.
  - **Clearing a field in an update:** an update is merged over the stored row, and JSON has no `undefined`, so `""` clears an optional field (`clearable` in `validation.ts`). Setting a card or an account clears the other, so an update never leaves both set.
  - **Resuming (#128, decided with Prathik 2026-10-21):** Resume and Restart store the date it starts again in `resumedOn` (a column added through the dev sheet-columns route). The renewals between its last payment before that date and the date itself weren't due, so they're left out rather than flagged. Only the latest restart is kept, so a gap from an earlier pause would show again after a second one.
  - **Deleting a subscription deletes its payments**, in one read and one write with the repository's `removeWhere`. Deleting row by row costs two requests a row against the Sheets quota (60 a minute), so 32 payments would run out. The payments go first, so a delete that fails half way leaves the subscription there to delete again.
  - **A rule across fields is checked on the whole row (#125).** A partial update can't check one from its own fields: editing only the amount of a Skipped payment can't see that the stored row is Skipped. So a repository can take a `check(row)`, which runs on each new row and on the row after an update is merged over the stored one. A broken rule writes nothing and throws `InvalidRowError`, which the route factories turn into a 400. Subscriptions and SubscriptionPayments use it. Any entity with a cross-field rule should too.

  Earlier passes over this plan never fleshed this tab out. "Monthly Average" and "Next Billing Date" are computed (see the fix below), not stored columns.

  **A latent bug caught on this pass**: an earlier version of this plan gave `Card`/`Subscription` a bare day-of-month number (`billingDay`, 1–31) to predict the next occurrence. That works for monthly billing, but the real data has yearly subscriptions too (Apple Creator Studio, F1TV) — "24" doesn't tell you April 24th vs any other month. Both entities now store a full `billingAnchorDate`/`statementAnchorDate`/`dueAnchorDate` (one known real occurrence) instead, and `nextOccurrence(anchorDate, cycle, from)` repeatedly adds the right interval (1 month, 1 year, ...) — correct for monthly and yearly alike, not just monthly. **Revised for cards in #75 (2026-10-19):** card statements are always monthly, so the yearly case never applies to them. A card now stores `statementDay` (1–31) plus `dueDayBuffer` (days to the due date), the shape of the old sheet and easier to enter. `Subscription` keeps its full `billingAnchorDate`, because it can be yearly.
- **IncomeSource** (name, alias, category: salary/investment/other, frequency: monthly/quarterly/yearly/one-time, expectedAmount, `status: active | inactive`) → has many **IncomeEntry** (incomeSourceId, `expectedDate`, `receivedDate` (nullable until received), amount, status: received/pending, `accountId`, tag: regular/bonus/other). The old sheet's single `incomeDate` column was ambiguous about whether it meant "expected" or "actually received" — `Loan`/`Card` already need that same expected-vs-actual split (`dueDate` vs `paidDate`) for their own due-date alerts, so `IncomeEntry` gets it too, consistently, instead of overloading one date column. The old sheet's "Monthly Equivalent" column (normalizing e.g. a yearly bonus into a monthly figure) is computed in `lib/aggregate/income.ts` from `expectedAmount`+`frequency`, not stored — same reasoning as Card utilization.

  **Income columns added for the page (#185, `docs/design/income.md` "The final design")**: `IncomeSources` gets a required `scheduleDate` (a day the source is expected; its schedule counts from it both ways, and it's a one-time source's only date) and optional `color` (`CARD_COLORS`: Emerald is the All sources colour), `icon` (`INCOME_ICONS`), `accountId` (where it usually lands) and `statementMatch` (text in a bank statement line that marks a deposit as this income, for the salary import in #187; `accountId` and `statementMatch` can be cleared with ""). `IncomeEntries` gets `origin` (`Manual` or `Statement`) and `statementRef` (the statement line it came from, so a statement read twice adds nothing). Pending and upcoming entries are computed from each source's schedule, never stored (PRD §8): a new entry must be `Received` with a `receivedDate`, while the row schema still reads an old `Pending` row. The math is in `lib/aggregate/incomeSchedule.ts` (scheduled dates both ways from `scheduleDate`, pending, upcoming, late) and `incomeYear.ts` (months by the day money landed, the received average, against last year, India's April–March financial year with its projection, pay changes); Overview's "Pending income" uses `pendingPayments` (#186). All went in through the dev `sheet-columns` route, which also fixed the Frequency dropdown's `Quaterly`/`OneTime` typos (both tabs were empty). RSU vests and ESPP purchases are never IncomeEntries: they're `InvestmentTransactions` with source RSU or ESPP.

  **Fix vs the old sheet**: `"Lending - Hotel Sonali"` appeared as its own `IncomeSource`/`IncomeEntry` (tagged category "Investment"), *separate from* the identically-named entries in `Lending Book`/`Lending Payments` — the same cash coming back from a personal loan was tracked twice. `Loans` is now explicitly scoped to bank-borrowed loans only (see the `Loan` entity below — lending-to-others tracking isn't part of this app for now), so this specific double-count can't recur here; the underlying principle still matters if lending tracking is ever added later — it should get its own tracking, not be folded into generic `IncomeEntry` rows. Genuine investment-adjacent income (e.g. an LIC policy payout) still belongs under `IncomeSource.category = investment` as before.
- **Loan** — scoped to personal loans borrowed from a bank; lending is a separate entity (see "Lent out"), so no `direction` field (`name` — a memorable label, since two loans from the same bank need something to distinguish them — `lenderName`, `category`: personal/auto/home/other, `repaymentStructure`: Standard-Emi (only option designed so far — see below), principalAmount, annualInterestRate, tenureMonths, `paymentFrequency` (Monthly only), processingFee, stampDuty, preEmiInterest, disbursementDate, `firstEmiDate`, `accountId` (disbursement account; blank only when `disbursedTo` is Seller), `disbursedTo` (Account or Seller: a car loan is usually paid straight to the dealer, so it never reaches his accounts; blank reads as Account), `status: active | closed`) → has many **LoanInstallment** (loanId, installmentNumber, dueDate, openingBalance, principalDue, interestDue, totalDue, status: pending/paid, amountPaid, paidDate, overdueCharge, `paidFromAccountId`/`paidFromCardId` (at most one set, same as `Statement`/`SubscriptionPayment` — an installment is occasionally settled via card, not just direct bank transfer)).

  Designed fresh via direct questions rather than inferred from the old sheet's numbers (its "Standard EMI" data turned out to actually be flat-rate — equal principal + flat interest on the original amount, not true amortization — which didn't match what was wanted going forward, so the old data was explicitly set aside rather than reverse-engineered). Confirmed: **true reducing-balance EMI**, a **predefined schedule with due dates** (not an open payment log), verified by property-based tests (principal fully repays to exactly zero, interest strictly decreases, EMI stays constant, due dates step correctly).

  The real fix vs the old sheet: `Debt Repayments` had the right headers but zero rows — nobody was going to hand-type a 12–36 row amortization schedule every time a loan was added, so it never got filled in, and its rollup columns had nothing to sum. Fix: when a `Loan` is created, its full `LoanInstallment` schedule is **generated automatically** (`lib/schedule/generateInstallments.ts`, one function per `repaymentStructure`) and written in the same call via the repository's new `createMany()` — so the schedule always exists from day one. The only manual step left per period is marking an installment paid (date + actual amount). `Total Paid`/`Outstanding Balance` are a simple, always-correct sum over those rows, computed in `lib/aggregate/loans.ts` — not stored on `Loan` itself. Other repayment structures (pre-deducted interest, interest-only, bullet) are deliberately not designed yet — `RepaymentStructure` only has one value until they get their own dedicated design pass.

  **Checked against a real loan (2026-10-25).** Prathik's HDFC personal loan agreement (₹11,10,000, 9.99% fixed, 12 EMIs of ₹97,581, due on the 7th) settled what the first design guessed or left open. `generateInstallments.test.ts` reproduces the agreement's own repayment schedule as a test.
  - **Monthly only.** The generator used to take Quarterly and Yearly but still applied the monthly rate and made one installment per month of tenure, so a 12-month quarterly loan came out as 12 payments over 36 months. Bank EMIs are monthly, so `paymentFrequency` now only allows `Monthly`. The column stays in case another frequency ever gets its own design.
  - **Due dates come from `firstEmiDate`, not the disbursement date.** EMIs fall on a fixed day of the month (HDFC: the 7th; disbursed on the 1st–20th, the first EMI is the next month's 7th, otherwise the month after). That rule is the bank's, so the loan stores the first EMI date from the sanction letter rather than working it out. Every due date counts from `firstEmiDate` itself, so an EMI on the 31st comes back to the 31st after February. Before this, each date counted from the previous one and stuck on the 28th for good.
  - **Rounding follows the bank.** EMI to the paisa, each month's interest to the whole rupee on the outstanding balance, principal is the rest. EMIs 1–11 match HDFC's schedule to the paisa. The last EMI repays exactly what the stored principals leave (₹96,775.83 against the bank's ₹96,775.80, which keeps more decimals), so outstanding still reaches exactly zero.
  - **The first EMI is a full month's interest.** The odd days between disbursement and the start of the EMI cycle are charged separately, up front, as `preEmiInterest` ("pre-EMI" or "gap" interest, ₹911 for 3 days on this loan).
  - **Charges come out of the disbursal; the EMI doesn't change.** The processing fee (GST included), stamp duty and pre-EMI interest are taken out of the amount paid into the account, while the EMI is still on the full principal. `netDisbursedAmount()` in `lib/aggregate/loans.ts` gives what actually arrived (₹11,00,920 on this loan, matching the agreement's Key Fact Statement). These are stored as the bank quotes them, not computed, for the same reason as an FD's `maturityAmount`.
  - **Still open:** overdue and partial payments. Prepayments are designed below. Loans like Prathik's Canara education loan (capitalised moratorium interest, then monthly interest on a running balance and irregular payments) won't be tracked: it's closed, and only EMI loans are in scope (2026-10-25).

  **Loans page columns (2026-10-26)**: nine optional columns on the end of `Loans`, added through `/api/dev/sheet-columns`, so a row from before reads as the defaults: `prepaymentEffect` (a row without one reduces the tenure), `color` (a row without one shows its category's: Home sapphire, Auto copper, Personal violet, Other teal; `loanColor()`), where the EMI usually leaves (`emiPaidFromAccountId` or `emiPaidFromCardId`, never both), and the bank's prepayment rules: `prepaymentChargePercent` (before GST), `prepaymentMaxPercent`, `prepaymentsPerYear` (April to March), `prepaymentsInLoan`, `prepaymentAfterEmis`. The icon comes from the category; there's no `icon` column (open decision 3's default).

  **Prepayments: designed 2026-10-25, built 2026-10-26** (the Loans page, `app/loans/actions.ts`; the math in `lib/schedule/prepayments.ts`). What the build settled beyond the design:
  - **The schedule is a function of the loan's terms and its prepayments** (`scheduleWithPrepayments`): the original schedule, then each prepayment's rebuild in date order. Saving, undoing and deleting a prepayment all write that target, so a loan's schedule never depends on the order things were entered in, and undo is exact. `planSchedule` turns the target into writes: pending installments are updated in place (keeping their ids), new numbers are created, and numbers that are gone are removed; **a paid installment is never touched**, even if the target disagrees with it. Writes go new rows first, changed rows in one batch, then the removals in one batch (bottom row first). If the rebuild fails, the prepayment row is removed and the schedule rebuilt without it.
  - **Which installments a prepayment replaces**: the ones after the last installment due on or before its date. An EMI paid over is anchored to that EMI instead (`afterInstallment`), so an EMI paid early with extra keeps its own amount. A manual prepayment dated before an EMI already paid is refused (date it after that EMI), and Close is refused while an earlier EMI is unpaid (mark it paid first), so a closed loan never keeps a pending installment.
  - **The month of a prepayment**: the first new installment's interest is the normal month on the new balance plus `dayInterest()` on the prepaid amount for the days since the last EMI (actual/365, to the rupee), still the proposed rule below. With a fixed EMI (Reduce-Tenure) the last installment repays what's left; with a fixed count (Reduce-Emi) the EMI is the annuity on the new balance over the same count, and the last installment takes the rounding. The bank's `bankEmi`/`bankInstallments` replace either.
  - **The charge** is filled in as the loan's percentage plus 18% GST, to the rupee (`prepaymentCharge`; 4% + GST of ₹50,000 is ₹2,360), and is editable to what the bank took. Rate steps (HDFC's 3% after 24 EMIs) aren't modelled: the charge is edited on the prepayment.
  - **Undo** (six seconds after Add loan, Mark paid and Add prepayment) and **Delete prepayment** use the same rebuild. Deleting a loan also deletes its prepayments.

  **The original design, as decided 2026-10-25:** Answers from Prathik: a prepayment sometimes shortens the loan and sometimes lowers the EMI, depending on the loan; **any amount paid beyond an EMI is a prepayment**; the app works out the new schedule itself and gets checked against the bank's revised schedule once a letter is available.
  - **New log tab `LoanPrepayments`**: `id`, `loanId`, `date`, `amount` (principal it pays off), `charge` (the bank's prepayment charge with GST, a separate debit that doesn't reduce principal; entered as the bank took it, default 0), `effect: Reduce-Tenure | Reduce-Emi | Close`, `source: Manual | Excess-Emi`, `installmentId` (set when it came from an EMI paid over), `paidFromAccountId`, and optional `bankEmi` / `bankInstallments`, the bank's figures from its revised schedule.
  - **New `Loans` column `prepaymentEffect`** (`Reduce-Tenure | Reduce-Emi`): the loan's usual effect, the default on each prepayment, and overridable on any one of them.
  - **Paying more than an EMI**: marking an installment paid with `amountPaid` at least ₹1 above `totalDue` + `overdueCharge` keeps the installment at its own amount and creates a `LoanPrepayment` for the excess (`source: Excess-Emi`, the paid date, the loan's `prepaymentEffect`). One action, both rows, so the excess is never lost in `amountPaid`. The ₹1 margin is because `totalDue` is kept to the paisa, as in the bank's schedule (₹97,581.47), while the bank debits whole rupees (₹97,581, the last one ₹97,582). A payment within a rupee of `totalDue` is that EMI paid in full, never a 17-paise prepayment or a 47-paise shortfall.
  - **Rebuilding the schedule** (pure, in `lib/schedule/`, one function used by every effect): paid installments are never touched. The pending installments due after the prepayment are replaced, starting from the outstanding principal less the prepayment. Installment numbers carry on, and due dates still count from `firstEmiDate`, so the day of the month doesn't move.
    - `Reduce-Tenure`: same EMI, as many installments as the new balance needs; the last repays what's left.
    - `Reduce-Emi`: same number of installments left, a new EMI from the annuity formula on the new balance.
    - `Close` (foreclosure): `amount` is the whole outstanding principal, every pending installment after it is removed, and the loan becomes `Closed`. This also fixes a closed loan keeping pending installments.
    - If the prepayment row has `bankEmi` or `bankInstallments`, the rebuild uses the bank's figure instead of its own. A mismatch with a bank letter is then fixed by entering the figure, not by changing code, and the letter becomes a test fixture like the HDFC schedule.
  - **Interest in the month of a prepayment (a proposed rule, to check against the first real bank letter)**: the agreement charges interest "on the outstanding daily balance", and the pre-EMI interest matched actual/365 (₹11,10,000 × 9.99% × 3/365 = ₹911). So the next EMI's interest is a normal month on the new balance, plus day-count interest on the prepaid amount for the days it was still owed since the last EMI: `round(newBalance × r/12 + amount × r × days/365)`. With no prepayment it is the usual EMI interest, unchanged.
  - **Writing it**: a prepayment touches two tabs, like loan creation. New installment rows are written first, then the old pending ones are deleted one at a time (concurrent deletes race). If writing the new rows fails, they are removed again and the prepayment isn't saved, so a loan never loses its schedule.
  - **Bank limits are warnings, not blocks.** HDFC allows a part-payment only after the first EMI, at most 25% of the outstanding principal, once a financial year and twice in the loan's life, at 4% + GST (3% after 24 EMIs, 2% after 36). The app records what actually happened, so it warns when a prepayment breaks a rule but still saves it. The rules belong to the loan, not the app, so they aren't hard-coded for other banks.
  - **What the page shows** (pure functions in `lib/aggregate/loans.ts`, each with a test):
    - Still owed stays the sum of pending `principalDue`, which is still right after a rebuild.
    - Prepaid is the sum of prepayment amounts.
    - Interest saved is the interest of the original schedule (regenerated from the loan's terms, not stored) less the interest actually paid and still due.
    - Months saved, or the EMI drop, comes from the same comparison.
  - **Charges sit beside interest, not inside it.** Prepayment charges go with the processing fee and stamp duty as the loan's charges. Cost of borrowing is shown in two parts: interest (pre-EMI interest included) and charges, with the total of both. Interest saved never nets off the charge paid to get it; both are shown, so a prepayment that isn't worth its fee is visible.
  - **Rate changes** (floating loans) can reuse the same rebuild later: a new rate from a date, with the EMI or the tenure changing.
- **InvestmentTransaction** — one unified log for both domestic and international trades (`market: IND | US`, `currency: INR | USD`, symbol, tradeType: Buy/Sell, `source`: Market/RSU/ESPP, quantity, price, total, assetType, broker, `settlementAccountId` — which account funded a buy or received sell proceeds; this was missing from the old sheet entirely, same gap as everywhere else the cross-cutting money-movement link now closes). Unified because the old sheet's separate `Investment Transactions (IND)` and `(US)` tabs were structurally identical — the same normalization reasoning applied to `Loan` before its scope narrowed to borrowed-only; confirmed to stay unified (Prathik raised, and didn't object to keeping, one log with a `market` field over physically separate tabs). **Positions/holdings are not stored as raw rows at all** — they're a computed aggregate (current quantity, average cost, gain/loss) derived from the transaction log, exactly like net worth is derived rather than formula-maintained. This is the direct fix for the old `Positions IND`/`Positions US` tabs' leftover helper-column and duplicate-row bugs: there is no separate mutable "positions" data to drift out of sync in the first place.

  **RSU/ESPP, scoped deliberately small**: rather than modeling full vesting schedules and grant lifecycles, an RSU vest or ESPP purchase is logged as an ordinary `Buy` — quantity = shares vested/purchased, price = the fair market value at vest (or the discounted purchase price for ESPP) — with `source` just tagging which acquisition type it was. Confirmed sufficient: Prathik only needs current holdings + cost basis, not full tax-lot/vesting detail.

  **FX rate — two genuinely different needs, kept separate on purpose**: cost basis in INR for a US trade needs the exchange rate *on that trade's date* — a historical fact that must never change once recorded, or past cost basis would silently drift whenever it's recomputed with a newer rate. So `InvestmentTransaction` carries its own `fxRateToInr`, captured once at entry time (mechanism — manual entry vs. auto-fetched — is decided alongside the price-source open question below, since it's the same class of problem). Current portfolio *value*, by contrast, needs *today's* rate, which is what the `Prices` tab's live rate is for. One field serving both would either misstate historical cost basis (if kept live) or misvalue current holdings (if frozen) — they can't be the same number.

  **Reviewed and tightened 2026-10-26** (`lib/aggregate/investments.ts`, `lib/sheets/investmentTransactions.ts`). A review of the design against the code found, and fixed:
  - **Same-day trades gave a cost that depended on typing order.** `computeHoldings` sorted on the date alone with a comparator that never said "equal", so a vest and its sell-to-cover on one date were folded in the order they were entered. Sell first, on a new position, left the cost untouched and the average at ₹13,333 instead of ₹8,000. Trades on one day now put the Buy first, and a test enters them both ways round (plus on top of an earlier position bought at another price). RSU vests with sell-to-cover make this a normal case, not an edge.
  - **A sell of more than was held made the position vanish.** It dropped out of the holdings with no sign anything was wrong, and a later buy started from a negative quantity. A sell now sells what there is, so a later buy starts clean, and `findOversells` returns each one (id, date, asked for, held) for a page to show as something to fix.
  - **Fractional units left float dust.** 0.1 + 0.2 − 0.3 is 5.6e-17, so a mutual fund sold out stayed as a ghost holding. A quantity under 1e-9 is nothing, and a position sold down to it is sold out.
  - **`currency` is derivable from `market`, but a row could disagree** (IND with USD was costed as INR). The schema now refuses it, either way round. The column stays in the Sheet for now: an `Instruments` tab (below) would make it go.
  - **The FX rate is only for US trades.** US needs it, IND must leave it blank. A rate of 0 is refused (it would cost the shares at nothing), as is a quantity of 0 or less. Price may be 0 (a bonus issue).
  - **`assetType` is a fixed list** (`INVESTMENT_ASSET_TYPES`: `Equity`, `ETF`, `Mutual-Fund`, `Debt-Fund`, `Gold`, `Other`), not free text. It doesn't repeat the market (a US stock is `Equity` on `US`), and RSU is a `source`, not an asset type. The real Sheet's column was already a DROPDOWN. The list is a default to change as holdings need.
  - **The rules across fields are one list** (`rowRules` in `validation.ts`), used as the create and row schema's refinement and as the repository's whole-row `check`. So a partial update (`market` to US, with no rate) is caught on the merged row, and a row on the Sheet that breaks a rule is left out and logged instead of being costed wrongly. `clearableToUnset` is `clearable` for a number or an enum: `""` comes out unset.

  **Still open from that review (proposed, not decided):**
  - **`total` is a stored value that can disagree with `quantity × price`.** The meaning of `total` with fees isn't settled (amount including brokerage and charges for a Buy, net of them for a Sell?), so nothing checks it yet.
  - **An `Instruments` tab** (symbol, name, market, `assetType`, the ticker used to look up its price, a fund code for mutual funds). `symbol`, `assetType` and `broker` are free text repeated on every row, the join-by-name fragility the id principle above exists to remove: a typo splits a holding, and a holding's `assetType` is read from its first trade only. Prices need the ticker mapping anyway.
  - **Realised gain is lost.** A sell removes cost but its proceeds are never used. Realised gain, XIRR and dividends need them; the sell's own frozen rate already gives the INR proceeds.
  - **Splits and bonus issues** have no way to be recorded.
  - **Net worth** counts investments at cost basis until live prices (F-IV-03) land.
  - **A US gain should split into price and rupee effect** ("mostly rupee depreciation"), and the page could show NetApp as a share of the portfolio (RSUs make it a concentration risk). Both are pure functions to add with the page.
  - **Tax is not modelled.** Weighted-average cost is right for tracking (ADR 0003). A tax view would need FIFO and the bank's tax exchange rate.

- **FixedDeposit** — money placed with a bank, structurally the mirror of a `Loan` (principal + rate + tenure) but without a repayment schedule: just a principal that grows to a bank-quoted maturity value (`name`, `bankName`, `principalAmount`, `interestRate`, `compoundingType`: Cumulative/Non-Cumulative, `payoutFrequency` (Non-Cumulative only), `startDate`, `maturityDate`, `maturityAmount`, `accountId`, `status`: Active/Matured/Closed). `maturityAmount` is stored as a fact the bank quotes, not computed — real FDs compound on conventions (quarterly compounding, day-count basis) that vary by bank, and guessing the formula risks being confidently wrong, the exact mistake avoided earlier for Loan EMI math. **Cross-cutting principle, revised**: money doesn't only move via bank accounts — a subscription or a loan installment is often charged to a *credit card*, which only becomes a real bank outflow later, when that card's statement gets paid. Treating every payment as "from an account" would double-count: once when the subscription is logged against an account, and again when the card's statement (which already includes that charge) is paid from the same account. So outflow entities — `SubscriptionPayment`, `LoanInstallment` payments, and `Statement.amountPaid` itself — carry **two nullable FKs, `paidFromAccountId` and `paidFromCardId`, at most one set**: paid directly from a bank account, or charged to a card (in which case it's *that card's statement*, not this row, that eventually reduces a bank balance). Named `paidFrom*` rather than bare `accountId`/`cardId` — caught while implementing `Statement`, which already has its own `cardId` as a parent reference (which card the statement belongs to); a second, differently-meant `cardId` would collide with it. `IncomeEntry` (an inflow) only ever needs `accountId` — income lands in an account, never "into" a card. `InvestmentTransaction` gets `settlementAccountId` instead (debited for a Buy, credited for a Sell — no card option, since funding a trade via credit card is niche enough to skip for now). The old sheet gestured at this once (a truncated "paid via card" column on `Subscription Payments`) but never applied it consistently, and never modeled the distinction between the two payment paths at all.

**Naming convention, confirmed against the real `Accounts` Table**: dropdown/enum values in the Sheet are Title-Case, hyphenated for multi-word values (`Spending`, `Emergency-Fund`, `Active`) — not camelCase. TypeScript union types mirror this exactly (e.g. `type AccountPurpose = "Spending" | "Investment" | "Emergency-Fund" | "Loan-Payments"`), since Sheets Tables validate writes against that literal dropdown text — a camelCase value like `"emergencyFund"` would fail validation or show as invalid. Every enum field on every future entity in this plan follows the same convention, even where earlier prose above still shows a lowercase/camelCase example.

Every entity gets a stable **`id`** (short UUID, generated on creation) as its primary key. The old sheet joined tabs by matching on human-readable names (e.g. "Card Name" text) — fragile, since renaming a card silently breaks every linked statement. Master tabs keep their `name` column for human readability when Prathik looks at the raw Sheet, but all cross-tab references and all app-level lookups use `id`.

### Insurance (F-IS-01, built 2026-10-29, [ADR 0010](adr/0010-insurance-terms-with-years.md))

A master and a row per period, like Subscriptions and their payments: a **`Policies`** row (kind, insurer, what it covers, the sum insured or IDV, status, paid-from, add-ons, notes) and a **`PolicyPayments`** row for each **term**, with `years` (1 to 5): the cover that one premium buys. The full column lists are in `docs/design/insurance.md`.

- **Derived, never stored:** a term's last day (start plus years, less a day), a policy's renewal date (the latest end of any Paid term), its state (In force, Renew soon, Lapsed, Cancelled, Not started, No term) and every figure on the page. They live in `lib/aggregate/insurance.ts`, pure and tested; a stored "lapsed" flag or end date would go stale the day after it was written.
- **A year of cover is not cash paid.** A year of cover is a term's premium over its years; cash paid is by the calendar year of the day paid. A three-year premium is all in the year it was paid, and the page says why that differs.
- **Renewing is recording the next term.** There is no Skipped status: a term nobody paid for is a lapse, worked out from the dates, including a gap before a late renewal. Cancel keeps every payment; only Delete (for a mistake) removes a policy and its payments, payments first.
- **Writes** go through `lib/insurance/policyWrites.ts`: Add writes the policy and its first term together and takes the policy back out if the term fails; Renew refuses an overlapping term and takes the term back out if the cover can't be moved.
- **The policy number is kept whole in the private Sheet and shortened to its last four characters on the server** before anything reaches the browser; a number that starts with "…" is refused on save, so the shortened one can't overwrite the whole.
- **Not built:** importing the policy PDFs from Gmail (a parser per insurer and an ADR of its own), claims, tax deductions, and premiums paid in instalments inside one term.

### Goals (F-GO-01 to F-GO-05, built 2026-11-02, `docs/design/goals.md`)

**A goal is an earmark, not money.** The money already sits in an account the app counts, so a goal never changes net worth. A master and a log, like Subscriptions and their payments: a **`Goals`** row (name, an optional `parentId` for a sub-goal, category, `necessity` Need or Want, `scale` Minor or Major (a time horizon Prathik picks, never derived), `amount`, optional `targetDate` and `dateType` Fixed or Flexible, `startDate`, `plannedMonthly`, `status`, and when bought `doneOn`, `actualCost` and one of `paidFromAccountId`/`paidFromCardId`) and a **`GoalContributions`** row for each set-aside or take-back (`goalId`, `date`, `amount` above 0, `kind`, an optional `accountId` and `note`). The tabs were created through the dev `sheet-columns` route (`planNewTable`).

- **Derived, never stored:** what's saved (set-asides less take-backs, never below 0), a parent's target and saved (its own part plus its live sub-goals; a Dropped or bought sub-goal leaves), its due date (the latest of its own and its sub-goals', and a sub-goal with no date reads its parent's), funded (saved at or above target, never above 100% on a bar), months left, what it needs a month, standing (Funded, Overdue, Behind, On track, No plan, Someday, Paused, Done, Dropped), the expected pace, the funding plan and every figure on the page. They live in `lib/aggregate/goals.ts` and `goalsOrbit.ts`, pure and tested; the sample from the design boards reproduces its figures (₹3,14,500 of ₹11,72,800 saved, ₹73,690 a month on each schedule, ₹27,000 in funding order).
- **Rules, confirmed by Prathik on 2026-11-02 (money math is asked, not assumed):** months left is whole months from today to the date, at least 1 while the date is ahead and 0 on or after it; what it needs a month is what's left over those months rounded up to the rupee, and an overdue goal owes it all now; on track means planned is at least required; the funding plan serves Fixed dates, then Needs, then the soonest, then the smaller, each month first giving each goal what it needs for its date and then handing the rest to the goals still open, and the minimum monthly amount is rounded up to ₹500.
- **A bought or dropped goal's money is released by its status**, not by a take-back entry, so Reopen and Restore are only status changes and the earmark check stays derived. A take-back can't exceed what's saved in that goal.
- **A goal with parts is one pot (2026-11-03).** A part is part of its goal: money is set aside on the goal and given to each part by hand, which *moves* it (a take-back on the goal and a set-aside on the part, same account, noted so the lists leave them out; `lib/goals/partWrites.ts`). So saved, target, earmarks, bought and dropped work as before, a part takes no set-aside of its own, and what's left in the pot covers the goal's own part. One `saveGoalWithParts` write adds, changes and removes parts and moves their shares, with a journal that puts it back on failure; `fillInOrder` (pure, in `lib/aggregate/goals.ts`) hands money out Fixed, Need, soonest, smaller. The sky has a planet per main goal with its parts as moons on pick; the table lists main goals only.
- **Buying a part** (`settlePartPurchase`, 2026-11-04): the form's *paid out of the goal's money* amount X is what the part ends up holding before it's marked Done, so a larger share returns to the goal's unassigned money and a larger cost is moved in from it; a goal with parts is funded only when every piece is covered (`isFunded`). Bought and dropped parts are shown by `settledParts`.
- **Writes** go through `lib/goals/goalWrites.ts` (tested against in-memory repositories): one level of sub-goals, a parent that exists and is open, an amount above 0 (only a parent with sub-goals can stand at 0), no buying a goal while a sub-goal is open, and a delete that removes contributions, then sub-goals, then the goal. Every toast has Undo for six seconds through a strictly parsed token (`lib/goals/goalUndo.ts`); undoing a delete recreates the goal, its sub-goals and every entry under their new ids.
- **The page** (`/goals`, `?goal=` picks one) draws every main goal as a planet in the Orbit sky (its parts go round it as moons when it's picked): its ring is the months left (square-root scale, the last ring 3 years or more, a red ring for overdue, a someday ring for paused or undated goals), its size the amount and its arc what's set aside. The planets' angles come from `placePlanets`, a pure deterministic rule that keeps every planet and its name clear of the others. `?demo` (development only) shows the design's sample data with states `empty`, `one`, `funded`, `overdue`, `over` and `earmark`, and never touches the Sheet. "Income less obligations" reads Overview's own monthly obligations (`lib/aggregate/obligations.ts`) and is labelled as not a true surplus.
- **Earmarks:** a set-aside can name the account the money sits in; the page and Overview warn (never block) when the earmarks in an account pass its latest balance.

### Lent out (money lent to people, built 2026-11-06)

Money Prathik has lent to friends, outside any bank. It is **not** a bank `Loan` (those are borrowed) and not a Fixed Deposit (no bank backs it), so it has its own two tabs and its own net-worth line.

- **`LentLoans`**: borrower, principal, start date, `interestMode`, and the terms of that mode.
  - **Accruing**: a yearly simple rate (`interestRate`). Interest builds up and is paid with the principal whenever the borrower pays (his ₹6,50,000 at 12% from October 2024).
  - **Paid-out**: a fixed `payoutAmount` every `payoutFrequency`, and the principal stays out until the borrower returns it (his ₹3,00,000 at ₹6,000 a month and ₹1,82,000 at ₹18,000 a quarter). Its yearly rate is worked out from what it pays (24% and about 39.6%), never stored, so there is no rounding.
  - `status` Active or Repaid, with a `closedDate` on a Repaid one. Two optional columns on the end (A1): `incomeSourceId` (only a Paid-out loan: the income source its interest arrives through, ADR 0014) and `color` (the shared palette; a row without one gets a stable colour from its id, `lentLoanColor`). The mode's fields are validated together (`lentLoanRules`): an Accruing loan must have a rate and no payout; a Paid-out loan the reverse.
- **`LentRepayments`**: money that came back, as `Principal` or `Interest`. Interest on a Paid-out loan arrives as **Income** instead (an income source per loan, matched to the bank statement), so these rows are mostly principal and an Accruing loan's interest.
- **Maths** (`lib/aggregate/lentOut.ts`, pure and tested):
  - Simple interest, never compounded: for each stretch of days, `principal still out × rate × days / 365` (actual days, 365-day year). Principal paid back stops earning from the day it is paid.
  - Owed today = principal still out + (accrued interest − interest paid, never below zero). A loan marked Repaid owes nothing whatever its rows say. A Paid-out loan accrues nothing here.
  - Nothing is stored: the accrued figure is recomputed from the loan and its repayments on every read, so it can't go stale.
- **Net worth**: `lentOutInr` is its own asset line ("Lent out"), added to net worth. It is owed by a person and can go bad, so it is never folded into Fixed Deposits. If the tabs can't be read, Overview says so under "What needs attention" and leaves the line out instead of failing.
- **The Lent page** (`/lent`, built 2026-11-07; design `docs/design/lent-out.md`): greeting, what needs attention, Who owes what, the interest clock, the loans table, interest coming up and money back, and the forms (add, edit, record a repayment, mark repaid, reopen, delete). A payout loan's promised payouts and what arrived are read from its income source (ADR 0014), whether the source was made with the loan or already existed. **Overview** shows the Lent out line, a Lent out tile that opens the page, and the page's late or missing payouts and long-out loans under "What needs attention" (`overviewAttention` in `src/app/lent/views.ts`).

### Overview (F-OV-05, built 2026-11-08, [`docs/design/overview.md`](design/overview.md))

The Overview reads everything and decides nothing new: every figure is one a page shows, or a tested pure function.

- **One loader, one model.** `app/overview/loadOverviewData.ts` reads every source once (core tabs plus EPF, lent out, goals, insurance, prices, each flagged when unreadable and never taking the page down); `model.ts` turns it into the model every view reads (investments at market value through `investmentOverview`, net worth through `computeNetWorth`, the month-end series).
- **Investments are at market value** on the Overview (cost for a holding with no price), the number the Investments page shows. `computeNetWorth` takes the value as an input and falls back to cost for every other caller.
- **Past net worth is rebuilt, not stored** (`lib/aggregate/netWorthOn.ts`): each part read as it stood on the day. A month before the first bank balance is left out, never drawn as nothing; the last point is the headline figure itself. It is an estimate (see F-OV-06 in the PRD) until real snapshots (F-OV-07) exist.
- **Keep in mind is each page's own attention list in one shape** (`app/overview/warnings.ts`, `loadWarnings.ts`): the pages' `attentionView`s, tagged with their page and ranked act now, soon, worth knowing. Fixed Income lends only a late EPF credit and a matured deposit; a source that couldn't be read is a warning of its own. **Coming up** (`events.ts`) is the next 30 days from the same helpers the pages use, and each event joins its warning by a `ref`.
- **Eight things** (`insights.ts`) are measures with their working shown, never advice; one with nothing to say is left out. **Future you** (`lib/aggregate/futureYou.ts`) is arithmetic on his records and on numbers he sets: loans follow their stored schedules to exactly zero; the bank, lent-out money and card bills stay as today; the defaults (amount added, EPF a month, the two rates) come from his records, say where from, and are remembered on the device.

### Expenses (F-EX-01, building since 2026-11-09, [`docs/design/expenses.md`](design/expenses.md))

What he spent each month, worked out from **the pool**: every account the app has, savings and broker cash alike, so a transfer between his own accounts or a wire to a broker is never counted.

- **The math** is `lib/aggregate/expenses.ts` (pure, tested; #391): spent = came in + borrowed + came back + sold − bought − lent out − the pool's change. Bought is Market buys and new deposits; RSU vests, ESPP purchases and the sell-to-cover (an RSU Sell on the same day and symbol as an RSU Buy) are left out, since no cash of his moves. Came back is a closed deposit's payout and every lent repayment; borrowed is a disbursal into one of his accounts, less what the bank kept; a loan paid straight to the seller (`disbursedTo` Seller) is never borrowed, whatever account it names.
- **Parts:** card bills by the day they were paid (amount paid, else the statement's total), EMIs in full (a manual prepayment and its charge too; an Excess-Emi prepayment is already inside its installment), subscriptions and insurance not charged to a card. Cash and UPI is the rest, one worked-out line on the month's last day, and can be below zero when records explain more than left the pool (shown, never hidden).
- **A month needs both ends.** Each account's latest balance on or before the last day of the month before and of the month. A savings account with none yet is held flat at its first (dormant Canara and SBI); a broker account with none makes the month unknown, which is every month before November 2026. A dollar account's change is taken in dollars and turned into rupees at the USD/INR close on the month's last day (today's rate when the saved closes run out), so a rate move on idle dollars is neither spent nor kept. This differs from ADR 0012's "today's rate everywhere" on purpose: a past month's spending is a fact of that month.
- **Big spends** (`BigSpends` tab: date, amount, name, category, paid from an account or a card, note; created 2026-11-09 through `/api/dev/sheet-columns`, round-tripped on the real Sheet; `/api/big-spends`, #392) explain a month and never add to it. A card one counts in the month its bill (the card's first statement on or after the purchase) is paid, and is "waiting" until then.

### The Trades page (F-IV-19, built 2026-11-08, `docs/design/investments.md` "The Trades page")

## Where business logic lives (key decision)

The old sheet's worst bugs came from putting logic in two unreliable places: Apps Script triggers overwriting cells, and cross-tab spreadsheet formulas that silently broke or were left half-finished. This design moves **all aggregation and computation into the Next.js app's TypeScript code**, and keeps the Sheet as a plain, dumb data store:

- Sheets hold only raw rows (one entity per tab, `id` + fields) — no formulas at all, not even single-row ones. An earlier pass over this plan carved out an exception for `Next Billing Date` (a proven-reliable Sheet formula in the old sheet), but then designed `Card`'s identical "next expected statement" feature as a code computation instead — same shape of problem, two different answers. Resolving that inconsistency in favor of the stricter rule: **every** derived value, including single-row ones, is computed in code. `Card` and `Subscription` share a `lib/aggregate/recurring.ts` helper (`nextOccurrence(anchorDate, cycle, from)`) for their "next expected date" logic, instead of duplicating the math or leaving it in a spreadsheet formula.
- No Apps Script triggers in this phase. If automation is added later (e.g. auto-marking overdue statements), it may only ever *append* rows to log tabs — never overwrite existing cells — consistent with the Secrets/safety posture already set for this project.

This directly resolves the root cause behind "values getting overwritten" and "broken formulas."

### Open question: live price & historical FX-at-entry data source

Two distinct needs, both still open (to be decided when the investments phase starts, not blocking the rest of this design):

1. **Current price per symbol** (and today's USD→INR rate), for mark-to-market portfolio value.
2. **The USD→INR rate on a specific past trade date**, captured once into `InvestmentTransaction.fxRateToInr` when a US-market row is entered, per the cost-basis-vs-current-value split decided above.

Two viable approaches to sourcing both:

- **`GOOGLEFINANCE` in a small, single-purpose "Prices" Sheet tab** (symbol → live price, current USD→INR rate), read by the app like any other raw tab. Zero new external dependency or API key, and it's what the old sheet was already relying on (its footer disclaimer about delayed/unavailable quotes came from this). `GOOGLEFINANCE` also supports historical currency lookups for a specific date, which could cover need #2 as well. Risk: doesn't reliably cover every Indian ticker.
- **A backend price-fetch module** (`lib/prices/`) calling an external market-data API server-side, consistent with "logic lives in code." More reliable/flexible for both current and historical lookups, but adds a new API key to protect (covered by the existing Secrets rule) and an external dependency.

**Revised 2026-10-26 (proposed; answered in the decision below):** the recommendation below has two problems. `GOOGLEFINANCE` is the only formula the Sheet would hold, against [ADR 0002](adr/0002-no-formulas-in-sheet.md), and every new symbol needs a row added by hand in the Sheet, which breaks the goal of never opening it to add data. The alternative is a price fetch in code (`lib/prices/`) that writes values into a `PriceSnapshots` log tab (date, symbol, price, FX rate). That keeps the Sheet formula-free, keeps working when the source is down (the last snapshot is used, marked stale), and the log gives portfolio value over time, which F-OV-06 needs. A spike on the real tickers and funds decides the source: `GOOGLEFINANCE` does not, as far as I know, cover Indian mutual fund NAVs (AMFI publishes them free, with no key); a free historical FX source can fill the trade-date rate on the trade form.

**Decided 2026-10-27 (Q2): prices come from code, not from `GOOGLEFINANCE`.** A spike ran against live sources on a representative basket (NTAP, VOO, QQQ, Reliance, Infosys, HDFC Bank, IRFC, NIFTYBEES, GOLDBEES, the Nifty 50, 25 mutual funds, USD/INR). Prathik's real tickers weren't available (the Sheet tabs are empty), so the spike is to be re-run on them before F-IV-03 is built.

| Need | Source | Notes |
|---|---|---|
| US stocks and ETFs, NSE stocks and ETFs, indices | Yahoo chart API (`query1.finance.yahoo.com/v8/finance/chart/<symbol>`) | No key, unofficial, no SLA. One call per symbol (the batch quote endpoint needs a login token); 60 calls took 1.2 s. NSE uses `.NS`. BSE only works by name (`RELIANCE.BO`), not by scrip code, so the quote ticker is stored separately from the trade symbol. |
| Indian mutual fund NAVs | AMFI `NAVAll.txt` | Official, free, one 1.5 MB file for every fund, dated the previous business day. No NAV on market holidays: use the latest on or before the date. |
| Mutual fund history | mfapi.in | History only. It matched AMFI on 25 of 25 funds once and lagged three days on one fund another time, so never use it for the current NAV. |
| USD/INR today | Yahoo `USDINR=X` (Frankfurter as a cross-check) | 95.14 against 95.18 in the spike. |
| USD/INR on a past trade date | Frankfurter (ECB rates) | Back to at least 2020; a weekend date returns the previous Friday. Within 0.05% to 0.27% of Yahoo on three dates. The broker's own rate differs by its markup, so this prefills `fxRateToInr` and stays editable. |
| Dividends and splits | Yahoo chart `events` | Ex-date, gross per-share amount. Feeds F-IN-03 and split detection. |

- **Don't prefill a historical trade price.** Yahoo's old closes are adjusted for later splits (AAPL on 2020-08-28 shows 124.81, the real close was 499.23). The price comes from the contract note.
- **`lib/prices/` sits behind one provider interface**, so a source that breaks (Yahoo is the risk) can be swapped for a keyed one (Alpha Vantage, Twelve Data, Finnhub: not tested) without touching callers. It is I/O only, like `lib/sheets/`; conversions stay in `lib/aggregate/`.
- **`PriceSnapshots` log** (date, symbol, price, currency, USD→INR rate, source): written by the fetch, read by pages. A failed fetch falls back to the latest snapshot and is shown as stale. The log is also the history F-OV-06 and XIRR need.
- **Not used:** Stooq (404 on every ticker, US included). `GOOGLEFINANCE` is dropped without being tested (the test needed a spreadsheet the service account can't create, and it would break ADR 0002). It stays the fallback only if Yahoo proves unusable.
- **Still to do:** re-run the spike on his real holdings; add the `PriceSnapshots` tab to the Sheet; write an ADR when the module is built.

Original recommendation: start with `GOOGLEFINANCE` for both (matches "reuse what already worked," no new secret to manage) and only move to a backend price API if specific symbols or historical dates prove unreliable. Either way, once `fxRateToInr` is written to a transaction row, it's frozen — never re-fetched or recomputed on later reads.

## Gap review: sources not yet in the design (proposed 2026-10-27)

**Everything in this section is a proposal. Nothing is built and none of it is decided.** It comes from a review of the PRD and this design against what a personal-finance and investment dashboard usually needs, asked "is any kind of source missing?" Each item has a PRD ID (`docs/prd.md`, "Proposed additions") and says what the PRD's §10 already put out of scope. Where an item needs a decision from Prathik, it's an open question there (Q9 to Q11).

**One principle needs a note.** "Derive, don't store" (PRD principle 2) is about values that can be computed from other rows. A **snapshot** isn't one of those: it records what was true on a date (a price, an exchange rate, what the app showed), and once that day has passed it can't be recomputed from today's rows. So snapshot logs hold raw facts, never totals that the components already give.

### P1: the numbers are understated, or can't be rebuilt later

1. **Net worth and price snapshots (F-OV-07).**
   - **Why now:** past prices, FX rates and FD estimates can't be reconstructed later, so every day without a snapshot is history lost. F-OV-06 (net worth over time) stays P2 and out of scope in §10: this is only the capture side.
   - **`NetWorthSnapshots` log:** `date`, then each component, not the total: bank balances, investments (and whether they were at cost or market), fixed income, valued assets, card outstanding, loan outstanding. The total is summed in `lib/aggregate`, like net worth is today.
   - **`PriceSnapshots` log (once prices land, Q2):** `date`, instrument, price, USD→INR rate. It also gives price history for XIRR and a benchmark.
   - **Writing:** one per date, a later one the same day replaces it (as balance snapshots do). A page render must not write, so it's a "Save snapshot" action plus a scheduled run once hosted (ADR 0007), the way the statement sync is scheduled.
2. **Valued assets: EPF, PPF, NPS, NSC and more (F-FI-02, widened).** Generalises the EPF/PPF proposal above, since one shape covers everything you read a value off a statement for.
   - **`ValuedAssets` master:** `name`, `kind` (`EPF`, `PPF`, `NPS`, `NSC`, `Insurance`, `Property`, `Vehicle`, `Other`), `institution`, `status`, `color`.
   - **`AssetValuations` log:** `assetId`, `date`, `value`: the same shape as Accounts and `BalanceSnapshot`, with a same-day replace and a stale warning after 30 days.
   - **`AssetContributions` log (optional):** `assetId`, `date`, `amount`, for a return figure.
   - **Net worth** sums each active asset's latest valuation. The app never computes the interest: EPF and PPF rates are declared yearly and NPS moves with its NAV, so the passbook or statement is the truth.
   - **An RD stays FD-shaped:** a generated monthly deposit schedule and a bank-quoted maturity amount.
   - **Open (Q9):** one entity for all of these, or one per kind.
3. **Foreign-currency balances, and cash at a broker (F-AC-05, decided 2026-11-05, [ADR 0012](adr/0012-foreign-currency-balances.md)).** Accounts have no currency field, so USD at the US broker (ESPP leftovers, dividends, sale proceeds before they're moved) has nowhere to live, and neither has an Indian broker's idle rupees. His example: $3,000 at the US broker and ₹1 lakh at the Indian one. Each is one account: `AccountType` gains `Brokerage`, purpose is the existing `Investment`, and `bank` holds the broker's name. **Built (#273 to #278):** the `currency` column and the `Brokerage` type on the Accounts tab; a pure `inRupees` (`lib/aggregate/accountCurrency.ts`) that converts at one boundary, right after the Sheet is read (`lib/prices/rupeeBalances.ts`, called by the Accounts, Goals and Overview loaders), so no aggregate learns about currencies; today's rate from `lib/prices/usdInr.ts`; a dollar account is left out of the totals, with an amber notice, when the rate can't be fetched, and can still be updated in dollars. The forms take dollars (a `$` prefix, "≈ ₹" in the preview, the 20% drop check in dollars), a Brokerage account asks for a currency, and a currency can't be changed once an account has a balance. The hero card, Balance history and the check-in show the dollars with the rupee value beside them. The Gmail statement import never matches a Brokerage account. **Still to build:** the Investments side (F-IV-18: the cash card, the greeting figure, *Paid from*), which waits for the Investments page; (the maths for it, `lib/aggregate/brokerCash.ts`: cash by broker, the idle share and a trade's effect on a cash balance, is built and tested, #279).
   - **`Account.currency`** (`INR` default, `USD`). A `BalanceSnapshot` is in the account's own currency.
   - **Value in INR** uses today's rate, with no frozen rate and no cost basis: cash has neither. The rate comes from the same source as prices (Q2).
   - **US trades** could then settle from a USD account as well as an INR one. A trade's `total` is already in USD, so a USD account takes it as it is. The remittance cost of moving INR to USD isn't modelled.
4. **Dividends and interest (F-IN-03).** `IncomeSource.category = Investment` already exists, but nothing feeds it.
   - **Indian dividends, savings-account interest and FD interest** credit a bank account with a narration, so the bank-statement read that finds salary (ADR 0009, `statementMatch`) can find these too.
   - **A Non-Cumulative FD's payout frequency** gives its expected dates, so a payout can be expected-versus-received like any scheduled income (`incomeSchedule.ts`).
   - **US dividends** land in the USD account as an entry in USD, with the tax withheld shown (gross against net). Dividends on RSU and ESPP shares are income; the vest and the purchase aren't (PRD, Income).
5. **Investing costs (F-IV-04).** Brokerage, statutory charges and tax withheld change what a trade really cost. This is the open meaning of `total`, and it blocks F-IV-01's acceptance criteria.
   - **Proposed:** keep `quantity`, `price` and `total`, and say `total` is the cash that moved, in the trade's currency: price × quantity plus charges for a Buy, minus them for a Sell. Charges are then `total` less price × quantity, derived and never stored. Cost basis already uses `total`, so fees are in it.
   - **Then add a check** that a Buy's total isn't below price × quantity and a Sell's isn't above it, with a tolerance for rounded prices (to settle against real contract notes).
   - **Tax withheld on a dividend** belongs to the dividend (item 4), not to a trade.

### P2: later

6. **Other asset kinds (F-IV-05).**
   - **REITs and InvITs** trade like equity: add `REIT` to `INVESTMENT_ASSET_TYPES`.
   - **Bonds and T-bills** are FD-shaped (face value, coupon, maturity) or priced instruments.
   - **Crypto** needs a market beyond `IND` and `US`.
   - **Insurance surrender value, property and a vehicle** are valued assets (item 2).
   - Add each only when there's a holding to track.
7. **Upcoming RSU vests (F-IV-06).** A list of the next vests (date, shares, an estimate at today's price and rate), **not counted in net worth**.

   - **This narrowly reopens §10's "vesting schedules"**: a list, with no grant lifecycle and no tax lots. Open (Q10).
8. **Insurance, rent and fees as obligations (F-SU-03).**
   - **Proposed (rent and fees only; insurance left, see the answer below):** reuse Subscriptions, not a new entity. Add categories (`Rent`, `Education`; `Insurance` is no longer one) and an optional `coverAmount`. Its renewal schedule already handles yearly anchors, paid-from and skipped payments, and Overview's monthly obligations would include them.
   - **Answered (Q11), 2026-10-29:** insurance is **its own page** (F-IS-01, built; see "Insurance" in the domain model and `docs/design/insurance.md`): a `Policies` master and a `PolicyPayments` row per term with a `years` length (two of his policies are single premiums for three years), not Subscriptions categories. Only rent and fees stay proposed for Subscriptions, and the `Insurance` category is no longer wanted.

9. **Goals and health metrics (F-OV-08).** Pure functions in `lib/aggregate` with tests, each from data already held:
   - Emergency-fund cover in months: the balance of accounts whose purpose is `Emergency-Fund`, over the monthly money-out the Accounts page defines.
   - Allocation against a target by market and asset type, with the drift. The targets are Prathik's own inputs: the app suggests none.

   - Debt-to-income on Overview. Loans already has EMI load against salary.
10. **Imports for holdings (F-IV-07).** Today everything except Gmail statements is typed by hand.
    - **India:** the emailed NSDL/CDSL consolidated statement (demat holdings) and the CAMS/KFintech one (mutual funds).
    - **US:** the stock-plan or broker statements, which carry RSU releases and ESPP purchases with the share price at vest or purchase.
    - **Same architecture as ADR 0006 and 0008:** Gmail, parsed, idempotent, and a disagreement waits for an answer. Each needs its own ADR and parser fixtures from real statements, so check what a real statement lists before designing.
11. **Foreign-asset disclosure data (F-IV-08), out of scope.** India's yearly return asks, as I understand it, for each foreign holding's opening, peak and closing value, plus income and sale proceeds. The peak needs daily prices, which monthly snapshots wouldn't give. Tax reporting is out of scope in §10, so nothing is built; it's listed so the price-history design doesn't rule it out. Check the requirements with an accountant first.

## Data storage layer (Google Sheets)

One tab per entity, `id`-keyed:

**Master/definition tabs:** `Accounts`, `Cards`, `Subscriptions`, `IncomeSources`, `Loans`, `FixedDeposits`, `Policies`, `EpfAccounts` (ADR 0011, built 2026-11-05)
**Log tabs:** `BalanceSnapshots`, `Statements`, `SubscriptionPayments`, `IncomeEntries`, `LoanInstallments`, `InvestmentTransactions`, `PolicyPayments`, `EpfEntries`, `EpfRates` (ADR 0011, built 2026-11-05)
**Log tab (investments, once prices land):** `PriceSnapshots` — date, symbol, price, currency, USD→INR rate, source, written by the app's price fetch (Q2, decided 2026-10-27). The earlier plan of a `GOOGLEFINANCE` `Prices` support tab is dropped.

Each log tab's rows carry a foreign-key column back to its parent (e.g. `cardId` on `Statements`) instead of a name string, plus — where the entity represents a real payment — the `accountId`/`cardId` pair described above. Column-level detail (which fields per tab) gets finalized when we implement the Sheets layer — the shapes above are already grounded in what worked in the old sheet, just re-keyed by `id`, de-duplicated (Loans replacing Debt+Lending), and with the derived/ambiguous columns (Opening Balance, Monthly Average/Equivalent, a single overloaded date field) removed in favor of computing them or splitting them, per the fixes above.

### Sheet format: Tables, not plain ranges

Every tab above is built as a Google Sheets **Table** (the structured-table feature — typed columns, built-in sort/filter, dropdown-type columns for enums), not a plain cell range with data-validation rules bolted on separately. This isn't a new idea introduced here — re-checking the old sheet confirms every tab actually inspected (`Card Setup`, `Statements`, `Bank Accounts`, `Debt Book`, `Income Statements`, `Investment Transactions`, ...) was already a Table (the colored status pills and per-column type icons seen throughout were Tables' native dropdown/date/currency column types). It's a genuinely good part worth explicitly carrying forward, not something invented fresh — just applied consistently this time, to every tab, by design rather than habit.

- Enum fields (`status`, `category`, `repaymentStructure`, `market`, `tag`, ...) use Tables' dropdown column type; date fields use its date type; money fields use number/currency.
- **Default to a Table for every tab; drop to a plain range + standard Data Validation only where a Table genuinely can't express something.** No tab is currently expected to be an exception: the `GOOGLEFINANCE` `Prices` tab that was the anticipated one is dropped (Q2), and `PriceSnapshots` is an ordinary log.
- **Open technical risk to verify during implementation, not assumed now**: when the backend appends a new row via the Sheets API (`googleapis`), confirm it lands *inside* the Table's range and inherits its column types/dropdowns, rather than landing as a plain row just below the Table. If the API's append behavior doesn't cooperate with Tables for a given tab, that tab is where we'd fall back to a plain range — this is exactly the kind of "only when Table is unusable" case to resolve empirically, not guess at now.

### Writing to Sheets (found 2026-10-17, #45)

Writes use `valueInputOption: "USER_ENTERED"`, which parses each value the way typing it into a cell would. Every field goes through `toUserEnteredCell` in `lib/sheets/cellValues.ts`:

- **Dates go as ISO text** (`"2026-08-05"`), so Sheets stores a real date and the Table's DATE column shows it as one. The original code sent date serial numbers instead. The Sheet then showed them as bare numbers like `46239`, while the app still read them back correctly, so nobody noticed until a real round trip looked at the displayed values.
- **All other text gets a leading apostrophe**, which tells Sheets to keep it literally. Without it, USER_ENTERED turned `"0425"` (a card's last 4) or a digits-only PDF password into a number that lost its leading zero, and would have turned text starting with `=` into a formula. The apostrophe isn't stored, and reads return the plain text.
- **Numbers go as numbers.** NaN and Infinity are refused, because JSON would turn them into `null` and silently clear the cell.
- **`RAW` was tried and rejected.** It keeps text right, but stores dates as bare serial numbers, which brings the original display bug back.

  **The page (#126)** splits the same way as the Cards page: `lib/aggregate/subscriptionPage.ts` works out the numbers (the carousel's order, each pick's facts, the payments table, the charged-to and category splits; pure, tested), and `app/subscriptions/views.ts` turns them into the design's words for every pick at once, also tested. The client components only render those views, so turning the carousel never waits on the server. The pick is kept in `?sub=` with `history.replaceState`, which the Next router follows without a server round trip. The chart (#127) works the same way: `lib/aggregate/subscriptionChart.ts` (Day by day's grid and the Payment trend, pure, tested) and `app/subscriptions/chartView.ts` (its words). The pick is kept by id, not by its place in the carousel: Next keeps client state across a refresh, and a refresh can reorder the carousel or drop a subscription.

  **A side-by-side layout that measures itself must not depend on the pick (2026-10-21).** The cost map fills the height of its grid row, so it ends level with the Payments and Charged to column, and squarifies its blocks at that height. The row's height came from the Payments card, which changed with the pick. Its height ran from 231 to 468px, the map's from 440 to 609px, and every pick moved the blocks. At xl, `PaymentsCard` now keeps one height: a hidden, `inert` table of six placeholder rows sits under the real one (in a `minmax(0,1fr)` column: a bare grid column is as wide as its widest content, so Price history, drawn first at a 520px fallback, measured itself instead of the card and overflowed it), and the line under it is always there. Anything laid out from its own measured size, like the map or a chart, needs the same: a size that doesn't follow what's picked.

  **The map's morph (1A) keeps the same elements.** A CSS transition only runs on an element that stays mounted. So By category doesn't render category tiles in place of the blocks: every block stays, keyed by its subscription, and `costMap.ts` gives it a box inside its category's tile. The tile itself is a transparent overlay with the name and total, carrying `data-map-key`. Its blocks carry `data-map-owner`, so `CostMapHover` lights them along with it. When testing in the browser pane, note that React builds pointer-enter and pointer-leave from `pointerover` and `pointerout`, so a synthetic `pointerleave` never reaches `onPointerLeave`.

  **The Renewals page (#130)** follows the Statements page: `lib/aggregate/subscriptionRenewalList.ts` (the period's renewals with where each was charged and how its payment compares, the filters and their counts, the groups, whole-month pages and the tiles; pure, tested), `app/subscriptions/renewals/views.ts` (its words, tested against the design's figures) and `params.ts` (the address). Every control is a link, a GET form or a menu of links built on the server, so the address always says what's shown. It doesn't change the renewal rules below; it only lists what `allRenewals` gives for the period. Its row actions use the Subscriptions forms (#128) through `useSubscriptionForms()`, plus three server actions in `app/subscriptions/actions.ts`: `updatePayment` (Edit payment, through `updateSubscriptionPaymentSchema`, so marking one Skipped records ₹0), `deletePayment`, and `markRenewalSkipped` (It didn't charge: a ₹0 Skipped payment for a renewal not recorded, refused once it's recorded, with Mark paid's Undo).

  **Renewals (#125, decided with Prathik 2026-10-21)**, in `lib/aggregate/subscriptionRenewals.ts` (pure, tested). Nothing stores a renewal: each one is computed from the schedule, and only payments are written.
  - **The schedule** is the billing anchor date stepped by whole cycles in either direction, never before the start date. Each date counts from the anchor itself, so a 31st anchor comes back to the 31st after a short month.
  - **A payment counts for a renewal when it's within half a cycle of it**, either side (about 15, 46 and 183 days). Renewals are settled in date order, each by the earliest payment in its window that hasn't settled an earlier one, over the whole schedule. So the answer never depends on the range asked for, and a late payment isn't taken by the next renewal (found in review: nearest-first matching gave Mar 10 to Mar 23 and flagged a paid Feb 23). A second charge in one cycle still counts as spend but doesn't settle the next renewal. A renewal that's passed with no payment is "not recorded".
  - **"It didn't charge" is a ₹0 payment with status `Skipped`.** It settles the renewal, so it isn't flagged, and adds nothing to spend or to the price history. The schema refuses a Skipped payment with an amount, and an update that marks one Skipped records ₹0. As for a subscription, `""` clears where a payment was charged, and setting one place clears the other.
  - **`Pending` stays in the model**, so a row that has it still reads, but nothing in the app writes it: an upcoming renewal is computed, not stored.
  - **Paused:** renewals stop after its last payment. **Cancelled:** they stop at its cancelled-on date. A renewal on that date doesn't happen either, unless it was paid, since people usually enter the day access ends. The first unpaid one on or after it is shown as "won't renew". With no cancelled-on date, they stop after its last payment.
  - **A price change** is a charged payment 2% or more different from the one before it, so small moves (a dollar-billed charge's exchange rate) are ignored. When the latest charge is 2% or more off the plan's price, the page offers to update the plan.
  - **Mark paid** is offered from 3 days before a renewal (today included). It records the plan's price on the renewal date.
  - **A month's spend:** the payments recorded in it, plus, from this month on, the active renewals still to come at the plan's price. So a past month is what was paid. A renewal marked paid ahead (Mark paid records it on the renewal date, which can be next month) counts in its own month as paid, never also as expected. A renewal not recorded isn't counted as expected; it's flagged instead.

### Changing a tab's columns (#124)

New columns and dropdown values are added through the Sheets API, never by hand in the Sheet. `lib/sheets/tableColumns.ts` (pure, tested) works out an `updateTable` request from a repository's columns and row schema:
- Missing columns go on the end, typed from the schema: an `isoDate` becomes a DATE column, a number DOUBLE, an enum a DROPDOWN with exactly the enum's values, and anything else TEXT.
- An enum column's dropdown is reset to the schema's values.
- Nothing is renamed, moved or removed, and other columns' types are left alone.
- A tab whose existing columns don't match the code's order is refused, so nothing is written over the wrong column.

In `next dev`, `GET /api/dev/sheet-columns?tab=Subscriptions` shows what would change and `POST` applies it. It's a 404 anywhere else. To use it for another tab, add the tab to the route's `TABS`. It set up the Loans and LoanInstallments dropdowns and Loans' new columns (2026-10-25). It has set up Subscriptions (#124), SubscriptionPayments' `Skipped` status (#125), and IncomeSources and IncomeEntries (#185).

### Reading from Sheets (#63)

Reads use `UNFORMATTED_VALUE` with `SERIAL_NUMBER` dates, so cells arrive as the Sheet stores them: a blank cell is `""`, a date is a serial number, and a number typed as text is a string. Every row goes through `readRow` in `lib/sheets/rowReading.ts` before anything sees it:

- **Each cell is cleaned up for its column**, using the kind the entity's row schema expects there (read from the schema itself, so the two can't drift):
  - a blank cell becomes `undefined`, so an optional field is simply absent;
  - a date serial becomes an ISO date;
  - number text becomes a number (`"38500"`, `"₹38,500.50"`);
  - a number in a text column becomes text.
  - A last 4 typed as `425` (its leading zero lost) still fails its own four-digit rule.
  - Number text is read by `parseAmountText` (`lib/format/money.ts`), the same parser the PDF import uses. It also accepts the typographic minus the app displays (`−₹6,400`).
  - A date serial's time of day is dropped, never rounded, so an evening time can't move the date.
- **Then the row is checked against the entity's row schema**: its create schema plus `id`, in the entity's own file next to the create and update schemas.
  - `createRepository` checks at load that the columns match the schema, and that the date columns are exactly the `isoDate` fields. A mismatch would fail every row of the tab, so it throws instead. `entities.test.ts` loads every repository, so a mismatch also fails CI.
  - A card's last 4 and colour are looser than on create: they may be blank on rows from before those columns existed. A statement's total due may be negative on create and read alike, for a credit balance (#51).
- **A row that fails is left out of `list()` and `get()`, and logged once** (`[sheets] CardStatements row 7 (id …) was left out: totalAmountDue is blank`).
  - The log has only field names and rule messages, never cell values, because a Cards row holds a PDF password.
  - A row with every cell blank is skipped without a report. A row with data but no id is reported.
- **`readAll()` still returns the failed rows**, with their cleaned cells and row numbers, for code where skipping one would do harm:
  - The statement sync's duplicate check counts a badly edited row as existing, so it never imports that statement a second time.
  - Deleting a loan also deletes installment rows that fail validation. If one of them has no id, it can't be deleted, so the loan isn't deleted either and the error names the row.
  - The sync also takes PDF passwords from invalid card rows. Their statements still open, and are reported as matching no card instead of as a password failure.
- **The pages show which rows were left out** (#73), since nobody reads the server log.
  - `cached.ts` caches each tab's `readAll()`, not its `list()`. So a page gets a tab's records and its skipped rows from one Sheets read, under the same tag: a refresh or a write clears the notice with the data.
  - A skipped row keeps only its row number and problems in the cache, never its cells.
  - `SkippedRowsNotice` words them with `skippedRowsNotice` (`lib/format/skippedRows.ts`): "1 row in CardStatements couldn't be read: row 7, total amount due is blank. Fix it in the Sheet, then refresh." The Cards dashboard and the Statements page show it for Cards and CardStatements.
  - A hand edit to the Sheet doesn't clear the cache, so the notice says to refresh, and the Statements page has the dashboard's Refresh button for that. Otherwise a fixed row stays reported until the 15-minute revalidate.
  - Fields are named as their Sheet headers in words (`totalAmountDue` is "total amount due"). A blank field reads "is blank", anything else "isn't valid": the schema's own message is never shown, so no rule message can ever echo a cell.
- **`update()` and `remove()` find invalid rows too, without logging them as left out.** An update starts from the cleaned cells, so it can repair a row: a number stored as text is written back as a number.
- **Typed Table columns convert typed text on their own** (found in the #63 round trip, 2026-10-18).
  - Writing `'12400` to a number column, or `'5 Jul` to a date column, stores a real number or date, apostrophe or not. Text columns do keep the apostrophe's meaning, so `0425` stays text.
  - So in this Sheet the realistic bad row is a blank required cell, or a value outside a dropdown. Converting number text still covers columns that aren't typed.

### Verifying the Sheet (#77)

The real Sheet's tab names and columns are ground truth, and `createRepository`'s load check only compares a repository with its own schema. So `npm run check-sheet` compares the real Sheet with every repository, with `npm run dev` running. It prints ✓ or ✗ per tab with each difference, and exits 1 if any tab differs.

- **What it checks, per tab**: the tab exists and holds one Table starting at A1, since reads assume the header is row 1 and `id` is column A. Then the columns:
  - every column is there, with nothing extra, in the code's order. Headers must be the field names exactly. Order is compared among the columns both sides have, so one missing column isn't also reported as every later column moving;
  - each column has the right Table type: TEXT for text, DOUBLE or CURRENCY for a number, DATE for an `isoDate`, DROPDOWN for a `z.enum()`;
  - a dropdown has exactly the enum's values. A value missing from the Sheet's list means writing it fails. A value only the Sheet has means a row with it fails the read schema.
- **What each column expects comes from the row schema**: `columnExpectations` in `rowReading.ts`, next to `columnKinds`, and each repository exposes the result as `expectedColumns`. A field type no Sheet column type is known to fit (a boolean, say) throws when the repository loads, like the other load checks, so `entities.test.ts` fails in CI.
- **The comparison is pure**: `compareTab` in `lib/sheets/tableStructure.ts`, tested against fixture metadata. `checkSheet.ts` makes one `spreadsheets.get` for titles and Table structure only (`tables[].range` and `columnProperties`), no cell values. Its `checkedRepositories` list must name every repository, and `entities.test.ts` fails if one is missing.
- **It runs through the dev-only route `/api/dev/sheet-check`**, a 404 anywhere but `next dev`. A plain tsx script can't import the `server-only` Sheets code, the same limit `scripts/ingestStatements.ts` works around.
- **Things the API does that the check allows for** (found 2026-10-19): it leaves out fields at their default. Column A has no `columnIndex`, a Table at A1 has no start indexes, and a column with no type has no `columnType`.
- **First run, 2026-10-19**: the Cards tabs (Cards, CardStatements) and BalanceSnapshots, SubscriptionPayments and IncomeEntries match. Seven tabs don't:
  - Accounts' `startDate` has no type.
  - Subscriptions' `category` is a dropdown, but the code takes any text. Its `billingCycle` dropdown has `Quaterly` for `Quarterly`.
  - IncomeSources' `frequency` dropdown has `Quaterly` and `OneTime` for `Quarterly` and `One-Time`. Fixed 2026-10-24 (#185).
  - Loans, LoanInstallments, InvestmentTransactions and FixedDeposits had the placeholder dropdown values `Option 1` and `Option 2`. Loans and LoanInstallments were fixed through `/api/dev/sheet-columns` on 2026-10-25 (when Loans also gained `firstEmiDate`, `stampDuty` and `preEmiInterest`); InvestmentTransactions and FixedDeposits on 2026-10-31 (#234), with `assetType` now a fixed list in the code too. After the change `npm run check-sheet` passes on every tab, and a real create, update (including the cross-field rules and clearing an FD's payout frequency), read and delete round trip was run on both and cleaned up.

## Backend architecture

Next.js (App Router), TypeScript:

- **`lib/sheets/client.ts`** — one authenticated `googleapis` Sheets client, built from a service account key loaded via env var. Server-only module (never imported by client components).
- **`lib/sheets/<entity>.ts`** (one per entity, e.g. `cards.ts`, `loans.ts`) — a repository exposing `list()`, `get(id)`, `create()`, `update()`, `delete()` against that tab. Full CRUD exists here from day one regardless of whether every page's UI uses all of it yet — this is what "future-proofed for write-back" means concretely.
  - **Confirmed during the `Accounts` proof of concept**: `spreadsheets.values.get` returns *display-formatted* strings by default (dates as locale strings like `"8/1/2026"`, money as `"₹50,000.00"`), not the raw values our types expect. Every repository call requests `valueRenderOption: "UNFORMATTED_VALUE"` + `dateTimeRenderOption: "SERIAL_NUMBER"`, and each repository declares which of its columns are dates (`dateColumns: [...]`) so the shared `createRepository()` helper converts Sheets' date-serial numbers to plain ISO strings on read (and back on write). Plain numbers need no extra handling once unformatted — only dates do.
  - **Also confirmed**: appending a row via `values.append` lands inside the Table's range and keeps its dropdown/column formatting — the open risk flagged earlier in this plan is resolved, verified against the real `Accounts` Table.
  - **New risk found during full Phase 2 verification (all 12 tabs, real linked data, then cleanup)**: `remove()` finds a row by re-reading all rows and computing its index, then deletes by that index. Firing several `remove()` calls concurrently against the *same* tab raced — row indices shift as each delete lands, so a concurrent call can compute a now-stale index. Sequential calls (one at a time) worked correctly every time; only concurrent calls against one tab failed. Not a blocker for a single-user app driven by one UI action at a time, but worth remembering if a future feature ever fires parallel deletes against the same tab (e.g. a bulk-delete action) — that would need to serialize per-tab, not fire concurrently.
  - **Performance/design review, fixed**: `update()` was doing two full-table reads (`get()` then a separate `findRowNumber()`) for one write, and `remove()` re-fetched spreadsheet metadata just to find a `sheetId` that never changes for a tab's lifetime. Both now share one `findRowAndRecord()` read, and `sheetId` is cached per repository instance after its first lookup. `get()` also wasn't cached at all (only `list()` was) — `lib/sheets/cached.ts` now derives a cached `getCached<Entity>ById` from the cached list (same cache entry, no risk of the two disagreeing) instead of leaving single-record lookups to hit Sheets live.
  - **Real gap found and fixed: no write path invalidated the cache.** All 12 entities' write routes called the repository directly with no `revalidateTag`/`updateTag` at all — meaning once real add/edit forms exist, a save wouldn't be visible for up to 15 minutes. Fixed by building `lib/api/createCrudRoutes.ts` (below), which wires `revalidateTag(tag, "max")` into every write, consistently, instead of relying on each route to remember it.
  - **Real gap found and fixed: no input validation at the write boundary.** Routes took `request.json()` and hand it straight to the repository — a malformed request could write a bad row straight to the Sheet, or blow up with a raw Sheets API error. Every entity now has a zod `create<Entity>Schema`/`update<Entity>Schema` colocated in its own `lib/sheets/<entity>.ts` file (kept next to that entity's repository config, not in a separate schemas file, so everything about one entity stays in one place), and the route factory rejects invalid input with a 400 and field-level errors before it ever reaches Sheets. This also caught a real domain rule worth enforcing: `InvestmentTransaction`'s create schema `.refine()`s that `fxRateToInr` is required when `market` is `"US"` — exactly the frozen-FX-at-trade-date design decided earlier, now actually enforced rather than just documented.
  - **Real gap found and fixed: `createLoanWithSchedule` wasn't transactional.** A failure generating the installment schedule *after* the `Loan` row was created would recreate the exact "loan with no schedule" bug from a different cause (partial failure instead of never-implemented). It now deletes the orphaned loan and rethrows if schedule generation fails. Symmetrically, deleting a loan through the plain repository would have left its installments behind as orphaned rows — added `deleteLoanWithSchedule()` so deleting a loan always deletes its installments too, sequentially (per the concurrent-delete risk noted above).
- **`lib/api/createCrudRoutes.ts`** — `createListRoute`/`createItemRoute` build a whole entity's GET/POST/PATCH/DELETE handlers from just its repository, cache tag, and zod schemas: validate input → call the repository → invalidate the tag → respond, with `NotFoundError` mapped to a 404 and any other error to a 500, consistently. Every entity's `route.ts`/`[id]/route.ts` is now ~4 lines calling this factory instead of ~30 lines of hand-rolled logic — **this is the concrete answer to "flexible for new feature addition": adding entity #13 means a repository file with a schema, then two 4-line route files, not rebuilding validation/caching/error-handling by hand again.** `loans`' routes stay custom (schedule creation/cascade-delete need the extra step) but still reuse the same `handleRouteErrors` helper for consistency.
- **`lib/schedule/generateInstallments.ts`** — pure functions, one per `repaymentStructure` (only `Standard-Emi` designed so far), each taking a `Loan`'s terms and returning its full `LoanInstallment` schedule. Called via `createLoanWithSchedule()` in the same operation that creates the `Loan`, so the schedule tab is never left empty like the old `Debt Repayments` tab was.
- **`lib/aggregate/recurring.ts`** — shared `nextOccurrence(anchorDate, cycle, from)` helper: adds `cycle`-sized intervals (monthly, yearly, ...) to `anchorDate` until it reaches or passes `from`. Each step counts from the anchor itself, so an anchor on the 31st comes back to the 31st after a short month (stepping from the previous result drifted to the 28th for good; fixed in #75). Cards use `nextStatementDate` in `cards.ts` from their statement day since #75; `subscriptions.ts` (next billing date) uses `nextOccurrence` instead of duplicating the same date math twice, leaving it as a Sheet formula, or the earlier bare-day-of-month version that couldn't represent yearly billing correctly.
- **`lib/aggregate/*.ts`** — pure functions computing derived views from raw repository data: net worth, per-category totals, monthly trends, upcoming due dates. Includes `lib/aggregate/accounts.ts` (month-over-month balance change from point-in-time `BalanceSnapshot` rows), `lib/aggregate/subscriptions.ts` (monthly-equivalent spend per subscription, next billing date via `recurring.ts`, spend-by-category breakdown), `lib/aggregate/investments.ts` (folds `InvestmentTransactions` into current holdings; cost basis in INR uses each row's frozen `fxRateToInr`, current value uses `Prices`' live rate — never the same number for both) and `lib/aggregate/fixedDeposits.ts` (current value estimate, quarterly compounding that lands on maturityAmount, clearly not the actual redemption value), `lib/aggregate/cards.ts` (per-card utilization = outstanding statement balance ÷ creditLimit, next-expected-statement date via `recurring.ts`, and per-statement payment variance = `amountPaid − totalAmountDue`, surfaced as over/underpaid), `lib/aggregate/income.ts` (monthly-equivalent income per source, normalized from `expectedAmount`+`frequency`; total received vs pending for the current month), `lib/aggregate/loans.ts` (total paid, outstanding balance, and next-due installment per loan, summed from `LoanInstallment`), and `lib/aggregate/netWorth.ts` (combines all of the above into the Overview formula above). **Built and verified**: all of these exist now, with 55 passing unit tests against fixture data, no live Sheets calls needed — including a caught-and-fixed real bug where `investments.ts` used weighted-average cost basis (a Sell removes cost proportional to the fraction of the position sold, leaving remaining shares' average cost unchanged) rather than guessing at FIFO. `investments.ts`'s current implementation returns cost basis, not live market value, since the price/FX data source is still an open question — `netWorth.ts` uses that as a stand-in for now, explicitly commented as such, not silently wrong-looking later.
- **Caching**: `lib/sheets/cached.ts` wraps each repository's `readAll()`, the records plus the rows it skipped, in `unstable_cache` (not plain `fetch` — the Sheets repositories call `googleapis`, which doesn't go through the global `fetch`, so Next's automatic fetch-caching never applies to them regardless), tagged per entity, with a 15-minute `revalidate` as a passive safety net. **Correction caught before it shipped in every page**: the plan originally said this caching lives inside the generic repository itself, but `updateTag` (the primitive picked below for the Refresh button and post-write freshness) only works inside Server Actions — never inside a Route Handler, which is exactly what the `/api/*` routes built for Phase 1/2 verification are. Baking `updateTag` into the shared `create`/`update`/`remove` would break the moment those routes called it. So caching lives at the *read* side (`cached.ts`, called from pages) instead, and each write call site invalidates its own tag with whichever primitive its context actually allows — a Server Action can use `updateTag`; a Route Handler needs `revalidateTag(tag, "max")` instead, accepting its weaker stale-while-revalidate semantics.
- **Verified against this Next.js version's actual docs, not assumed from training data** (`next dev` flags this version as having breaking changes from older Next.js): the single-argument `revalidateTag(tag)` is deprecated here — it now requires a second `profile` argument (e.g. `"max"`) and, even then, only gives stale-while-revalidate semantics (serves old data now, fetches fresh on the *next* visit) — not what a "Refresh" button should feel like. The better fit, and what this app uses instead: **`updateTag(tag)`**, callable only from Server Actions, which blocks until fresh data is fetched — a "read-your-own-writes" primitive. Both the manual **Refresh** button and every write (`create`/`update`/`delete`) are Server Actions that call `updateTag` for the entity/entities they touch, so "Refresh" actually means refreshed, and the UI never shows stale data after an edit.
- **Gmail statement sync: what it remembers lives in the Sheet (#82).** It used to keep the Gmail message IDs it had handled in a local file, `state/processed-gmail-message-ids.json`. A host like Vercel can't write to the app's folder, so there the save at the end of a sync would fail after its statements were written, and every sync would read every email again. Two tabs replace it, both written only by the sync (no routes):
  - **`StatementEmails`**, one row per statement email read: message ID, date, subject, card, result (`Imported` / `Duplicate` / `Failed`), details, the statement it added or matched, tries, last tried. `lib/statementIngestion/emailLog.ts` decides what a sync reads: emails never seen first, newest first, then the failures again. An email logged as done comes back if its statement has been deleted from the Sheet, so deleting a wrong statement row is how to import it again. Picked over a "Processed" Gmail label, which needs write access to the mailbox (`gmail.modify`) and drifts from the Sheet when a statement is deleted.
  - **`SyncRuns`**, one row per sync, with how it was started (`Manual` / `Scheduled`), when, and what it did. A sync adds its `Running` row before anything else, reads the tab back, and stands down unless its row is the earliest live `Running` one (`syncTurn.ts`). Sheets has no conditional write, but appended rows land in one order that every reader sees, so two syncs started together agree which one goes ahead. A `Running` row older than 5 minutes belongs to a sync that died, and is marked `Failed`; every SyncRuns write after the first is best effort, so a failed status write never turns into a failed sync.
  - **Writes are batched, because of the Sheets quota (60 writes a minute per user).** Writing a statement and a log row per email would cost 2–3 requests each; a first sync of 35 statements would hit the quota. A sync reads emails, then writes all its new statements in one `createMany`, then the log rows in one `createMany` plus one `updateMany` (added to the repository factory for this: one read and one `values.batchUpdate`). Statements go first, so an email is never logged as imported without its statement; a sync that dies before the end logs nothing, and the next one reads those emails again, the Sheet's duplicate check (same card and statement date) catching any statement already written.
  - **Time limits.** A sync stops starting new emails after 45 seconds, and the sync route sets `maxDuration = 60`. The result says how many new emails are left, and the Sync button and `scripts/ingestStatements.ts` call again until none are (10 rounds at most). Failures it didn't get to retry aren't counted, so those calls always finish: each one reads at least one new email. One email gets 20 seconds, then it's logged as failed so it can't block the rest; an `AbortSignal` stops it changing anything if it finishes late.
  - Gmail is listed page by page (500 IDs a page). It used to take only the newest 50, so a first sync would have missed older statements.
- **Reading statement PDFs: checked against real statements (#56, 2026-10-19).** Every labelled email (35, five cards) was run through the import read-only, and each field was compared with the PDF's own text, laid out by position. Before the fix, only YES was right. HDFC read no total or minimum, ICICI and Axis read the wrong total, and CSB read the wrong due date. The causes were:
  - **The bank parsers were ported from a pypdf-based reference, and pdf.js extracts text differently.** `decryptAndExtractText` joins a page's text pieces with spaces, with no line breaks inside a page. So a pattern that needs `\n` never matches in the real text. A glyph can also be a piece of its own: HDFC's "C" rupee sign arrives as `C 5,000.00`, with a space. pdf.js can also map a glyph to a different character: ICICI's rupee sign is a backtick, not the reference's `Á`. Write a parser fixture the way pdf.js lays the text out, not line by line.
  - **The order of pieces is the PDF's, not the page's.** Axis's payment summary comes out as its labels, then the statement period and dates, then the total and minimum. The number after `=Total Payment Due` is the previous balance: the first term of the account summary's equation.
  - **The generic fallback filled gaps from anywhere in the text.** With ICICI's own pattern failing, it took both amounts from a worked example of the minimum-due calculation on a later page. Since #89, `parseStatement` uses the generic patterns only for a bank it doesn't recognise. A known bank's missing field leaves the statement incomplete, so a layout change shows up as a skipped statement instead of wrong numbers. On the 35 real emails the fallback filled nothing anyway. The flip side: a bank whose parser was never checked against a real PDF (SBI, Kotak, Amex) loses the generic wordings it leaned on. So adding a card from a new bank means checking its parser on a real statement first. Since #92 the import doesn't use the generic patterns at all (next point).
  - **The card picks the parser, not the PDF's text (#92).** `detectBank` returns the first bank in its keyword list (HDFC first) named anywhere in the text, so a statement that mentions another bank would be read by that bank's parser. `processMessage` now matches the card from the subject before parsing. `checkStatementBank` (`lib/statementParsing/issuerBank.ts`) maps the card's `issuer` to its parser. After the PDF is opened, but before its fields are parsed, the email is skipped if the issuer has no parser, or if the text doesn't mention the issuer's bank (`mentionsBank`, by `detectBank`'s keywords). The reason then names the bank `detectBank` finds instead, if any. A statement that names its card's bank and others too, in an ad say, is read by the card's bank's parser. Comparing with `detectBank`'s pick would have skipped it, since that pick depends on the list's order. Every issuer is in the map, so a new one in `CARD_ISSUERS` needs a decision there. An issuer with no parser, "Other" included, is skipped rather than read by the generic patterns (decided with Prathik, 2026-10-19). The reason says to fix the card's issuer in the Cards tab if that's what's wrong. With the card known earlier, these skips and the unreadable-fields one now log its card. The checks run in this order: PDF, password, card, bank, fields, last 4, duplicate. The card match needs only the subject, so it could come before the download, saving a download and a decrypt for each email that matches no card. It doesn't, so a no-PDF or locked email still says that first.
  - **A field the PDF doesn't have is left out, never guessed.** HDFC's credit-balance statement says the due date is "Nil". CSB's bill due at once says "Immediate", and a closed card's last one has none. Those statements are skipped as incomplete. Whether to import them anyway, and with what due date, is still open.
  - `toStatementFields` now also applies the Add statement form's two rules: the due date after the statement date, and the minimum at most the total (₹0 with a credit balance). A misread date or amount is skipped instead of written. That's what would have caught CSB's due date.
  - **A skipped statement says why (#89).** `toStatementFields` returns `{ fields }` or `{ problem }`, and the problem is the email's reason in StatementEmails. There are four kinds: the fields it couldn't read ("couldn't read the due date from the PDF"), a PDF that says there's no due date (`noDueDate`: HDFC's "Nil" when nothing is owed, CSB's "Immediate"), a due date not after the statement date, and a minimum above the total. Like the skipped-rows notice, a reason names fields and never their values (`fieldLabel` and `listOf` from `lib/format/skippedRows.ts`).
  - A statement can open with another card's saved password, since the sync tries every card's. So a card with no password saved can still import, and removing one card's password can stop another card's statements opening.

- **The Sheets quota: 60 reads and 60 writes a minute per user (found 2026-10-20).** One-click Mark paid did nothing when clicked. A burst of page loads, mostly testing, had used up that minute's reads, so the action's first read threw, and nothing caught it.
  - **Retries:** the Sheets client retries a request Google turns away for quota (429) three times, 1s, 2s and 4s apart (`retryConfig` in `lib/sheets/client.ts`). A turned-away request wasn't carried out, so retrying a write is safe too.
  - **Past that:** every card action catches the failure, reads included, and says Google Sheets is busy and to try again in a minute (`lib/sheets/errors.ts`). It shows in the dialog's alert (`FormState`'s `failed.message`) or in the quick-pay toast.
  - **No answer isn't retried, and a request times out (2026-11-05).** The Update balances dialog sat on "Saving…" with no way to tell slow from stuck. The Sheets client had no timeout, so a request that never answered waited for ever, and the library's default retried a request with no response twice, even a POST, which can add a row twice if the first one did land. `lib/sheets/client.ts` now gives each request 20 seconds (`SHEETS_REQUEST_TIMEOUT_MS`) and sets `noResponseRetries: 0`; only a 429 is retried, because only that one is known not to have been carried out. A read that gets no answer isn't retried either (a timed-out read would otherwise cost three 20-second waits); Refresh recovers it. A save that ends in a timeout says it "may or may not have been saved" (`isTimeoutError` in `lib/sheets/errors.ts`), never "nothing was written", because the request may have landed.
  - **A check-in is two Sheet calls however many accounts (2026-11-05).** `writeBalances` in `app/accounts/actions.ts` used to write one balance at a time: an append each, or a full re-read of the tab plus a write each for a day that already had one, so a check-in of eight accounts ran 10 to 20 sequential calls. It now makes one `updateMany` for the balances replacing a day's and one `createMany` for the new ones, updates first, so the Sheet is still never written concurrently. A failure between the two leaves the replaced ones replaced; saving again replaces them again rather than doubling them, and the dialog says some may already be saved. `saveCheckIn` logs where its time went (`[accounts] saveCheckIn: … ms`). Dialogs built on `FormDialog` show "Still saving… 5s" after four seconds of saving.
  - **Keep page loads down while testing:** each fresh load of the Cards page reads several tabs. Park a browser tab you aren't using on `/favicon.ico`.

- **Bank account statements from Gmail (ADR 0008, built and run against real email 2026-10-23).** The twin of the card import, for HDFC, Slice and Jupiter. `lib/accountStatementParsing/` (a parser per bank, `matchAccount`), `lib/aggregate/statementBalances.ts` (pure: checking a statement, the balances it gives, the decision per balance, reviews), `lib/accountStatementIngestion/` (`planStatements.ts` pure planning, `run.ts` reading and writing), `POST /api/account-statements/sync`, and `app/accounts/reviewActions.ts` (answering a review). Tabs: `AccountStatementEmails` (the email log), `BalanceReviews`; columns `BalanceSnapshots.source`, `Accounts.statementPdfPassword`, `SyncRuns.kind`.
  - **The statement must add up.** `checkStatement` requires opening plus each row to equal that row's printed balance, and the last to equal the closing balance. That one check is what proved each parser read the right columns on the real PDFs, with no figure shown: every real statement (995, 872, 68, 49, 27 and 26 rows) chained exactly on the first try after the layout quirks below were fixed.
  - **Quirks found on the real PDFs, which fixtures must copy:** *Slice*: every page repeats a "period page" header that starts with a date, so it must be stripped before rows are read or a page's first row takes the header's date; a page's footer has a grievance line after the support line, which glued a page's last row to the next page's first until it was stripped; amounts print with as many decimals as they need (₹500, ₹99.9); the older (January 2026) layout's font makes pdf.js extract every hyphen as a digit, so a debit reads `7₹300.5` and `31-Dec-2025` reads `317Dec72025`: any character stuck to the ₹ is the debit's sign. *HDFC*: the details block has the account number as the second `:` value after "Limit"; September's interest is posted the next day (1 Oct) but valued 30 Sep and is in the closing balance, so a row posted after the period's end but valued within it counts on the last day; a combined statement can hold several accounts, told apart by account number; its summary lists the four amounts in an order not relied on. *Jupiter (Federal Bank)*: a row has one amount, and the Dr/Cr after the balance is the *transaction's* (a UPI payment out reads Dr, with a positive balance after it), not the balance's; the grand total at the end is checked against the rows; the opening balance is printed without Dr/Cr; amounts have no thousands separators.
  - **Detect the bank by layout, not name.** A UPI narration in one statement names the others (`okhdfcbank`, "Payment from slice"), so each parser has a structural marker and Slice, whose marker is the loosest (its name), is tried last.
  - **Slice's round-up (atom) account explained a constant ₹13 gap** between the monthly statement and the range statement. The range's balance column is savings plus atoms; the monthly's savings section is savings alone, and its "Round ups atom" section and "Total closing balance (incl. atoms)" line give the rest. The monthly parser adds the atom opening and closing balance to its own and checks the total it prints. Found by lining the two up by date: one change point, then a constant difference, which meant a missing amount, not a wrong row.
  - **Overlapping statements are the cross-check.** Applying every email to a copy of the Sheet's balances showed the six real statements agree on every shared day once Slice's atoms were counted. An opening balance for a day that already has a balance is compared like any other, so two statements that disagree about a shared day open a review.
  - **Found in the first code review (2026-10-23), all fixed:** (1) a combined PDF could number your one unnumbered account from another account's statement, so `fillLast4` is only allowed when the PDF holds one statement; (2) answering a review checks that the balance it named is still for that account and day, since Edit balance can move one to another day; (3) the opening balance is created whenever nothing is recorded for that very day, not only when nothing is recorded before it, because carrying an older balance forward misstates the days between; (4) the CRUD list/item routes take a `serialize` function, and `/api/accounts` and `/api/cards` use `toClientAccount`/`toClientCard`, so a statement PDF password never leaves the server through an API route; (5) `BalanceSnapshots.source` becomes Manual when a balance is typed over (Update balance, or Edit balance with a new amount) and Balance history says "from a statement" for Statement ones; (6) a review shows the balance recorded now, not the one when it opened, and drops out when an edit has made the two agree; (7) the attention list is computed once per render; (8) the Sync button, its rounds and its re-read are one hook (`useSyncRunner`) for Cards and Accounts; (9) a scheduled run leaves out emails that failed in the last day.
  - **Month-ends need no row for a month with no transactions**, since carrying the last balance forward gives the same figure; the statement's last day gets the printed closing balance, so a range ending mid-month closes on its own last day.
  - **A review never changes a balance by itself.** `planReviews` skips the same statement value already raised (open, kept or accepted) and supersedes an open one when a corrected statement gives a different value. Answering writes the balance first and closes the review after, so a failure between them leaves the question open to answer again.
  - **Reviews and balances show money to the paisa** (`formatInrExact`): a ₹13 gap is the point, and a rounded figure would hide it.
  - **Writes are batched, in this order:** balances (one `createMany`), reviews, superseded reviews, last 4s, then the email log, so an email is never logged done without its balances. A sync that dies before the log writes nothing logged, and the next one finds the balances already there and adds none twice. To read a done email again, delete its row in `AccountStatementEmails`.
  - **New tabs are created through the Sheets API:** `planNewTable` (in `tableColumns.ts`, tested) makes the tab, writes its header row and a Table over it, typed from the row schema, through `/api/dev/sheet-columns` in `next dev`. The new Table has one empty first row, which the repository ignores. Only the two new tabs may be created this way; existing tabs are never created over.

## Frontend architecture

- **The details card's interactions (#117, all seven of section 6 in `design/cards-interactions/CardsInteractions.html`, Prathik's pick 2026-10-20).** `DetailsCard` stays a server component; the interactive parts are small client pieces, and their geometry is pure and tested in `detailsGeometry.ts`.
  - **A · Limit bar** (`LimitBar`): moving along it with a mouse, a finger or the arrow keys shows the amount at that point to the nearest ₹1,000 (`readLimitAt`), snapping within 10px to what's used and to the average's pill, which steps aside meanwhile. The keys use a snap narrower than a key step, so they can always move off one.
  - **B · Rolling digits** (`RollingNumber`, `digitColumns`): every number on the card rolls digit by digit instead of counting up. Each digit is a column of 0–9 keyed by its place from the right, which works because Indian grouping is fixed from the right, so React keeps the column and CSS slides it. There's no state, so it renders on the server too; columns are one `lh` tall, so they fit any line height. The columns are `aria-hidden` and unselectable, with the number beside them as screen-reader text, so copying gives the number rather than every column's ten digits.
  - **C · Header light** (`DetailsHeader`): the tile glare's light follows a mouse or pen, and `data-lit` spreads the rings (`group-data-lit/head`). Tailwind's `scale-*` sets the separate `scale` property, so check `scale`, not `transform`, when inspecting it.
  - **D · Figures that point** (`DetailsFigures.tsx`): a context shared by the figures, the limit bar and `MonthsChart`. Available lights the free part of the limit; the month figures open a chart of the period's months (`CardDetails.months`, the same months as the average) with that month picked out. Letting go waits 80ms, so moving between figures doesn't blink the chart. On a phone a tap toggles it.
  - **E · Bill focus** (`NextDue`): hovering a bill or its name widens it to at least 55% (`dueBarLayout`) with its name, amount and date as space allows. Clicking or tapping a name pins it.
  - **F · By due date:** a switch turns the bar into a timeline from today to three days past the last bill, each bill a dot whose area follows its amount (`dueTimeline`), with labels that would overlap hidden. It's the same elements, so they morph. The bar's slots are `calc()` fractions of its width less the gaps, so it lays out right before it's measured, on the server too.
  - **G · Paid bills fold away:** `nextSlots` compares the bills with the last render. One that's gone on the same card turns green ("✓ Paid") for 550ms, then folds to nothing while the rest close up. Gone because another card was selected, it just folds. A new bill, or one back after Undo, grows in. This is the only way the card knows a bill was paid: the payment's `updateTag` re-renders it with the bill gone.
- **The Subscriptions hero's interactions (#148, sections 2 and 4 of `design/subscriptions-interactions/SubscriptionsInteractions.html`, specced in `docs/design/subscriptions.md`).** They follow the details card's patterns: `RollingNumber` for the figures, and pure, tested geometry for reading the cycle bar (`cycleGeometry.ts`, like `readLimitAt`). Found while building them:
  - **A transition needs the same element on both sides of the change.** The stats were keyed by their label, which differs between picks ("A month", "Monthly"), so every figure remounted instead of rolling; they're keyed by place now. `CycleBar` renders one tree for All and for a subscription, only switching the slider's attributes, so the fill's width still slides between them. And Mark paid, Paid and Record payment are one `FormTrigger` in one place, so focus stays on it as it changes.
  - **A child turning inside a 3D-turned parent needs `transform-style: preserve-3d` on the parent.** Without it the child's `rotateY` is flattened into the parent's plane, so the peeking cover just got narrower instead of facing you.
  - **To move something on hover, move a child and keep the hovered element still.** A cover that slid its own box away could leave the pointer behind and flicker on and off. Only the face moves, so the cover stays under the pointer.
  - **Inline styles win over classes.** The cover flow sets each cover's `z-index` inline, so the peek's is `hover:z-[60]!`. The face's inline `transition` had to move into classes before reduced motion could turn it off.
  - **Checking Mark paid without the Sheet:** sample data can't be changed, so 4B was checked with a temporary, uncommitted stub of `markRenewalPaid` behind `?demo`, which kept the payment in memory and called the same `updateTag`. The server's re-render brought Paid, the emptied bar and the new Paid so far in one commit. In the Browser pane, `dispatchEvent(new PointerEvent(...))` with `pointerType: "touch"` drives React's handlers, for checking touch.
- **The Subscriptions chart's interactions (#149; the spec is "Built: the chart's interactions" in `docs/design/subscriptions.md`).** What's not obvious from the code:
  - **Day by day draws 365 buttons, so hovering never re-renders them.** The cells are memoised. The hovered day (or month total) is marked with `data-active` and `aria-describedby` in the DOM, as `HeatmapHover` does, and only the card's content is state. A cell redraws only when the range, the spotlit month, the pick or the tab stop changes.
  - **One tab stop, with a roving `tabIndex`.** The arrow keys move focus over every drawn day, empty ones included, so Shift-arrow ranges can start and end anywhere. `stepDay` and `dayAtPoint` (`chartGeometry.ts`, tested) do the grid's arithmetic.
  - **A drag reads the day from the pointer's position (`dayAtPoint`), not from the element under it.** A mouse or pen captures the pointer once the drag reaches a second day, so the drag keeps tracking past the grid. A finger's pointer is captured to its first cell by the browser anyway.
  - **Until then nothing is captured**, so a press let go outside the grid never reaches it (found in review: the next hover became a drag with no button held). A pointer move with `buttons === 0` ends the press. Capturing at `pointerdown` instead would move the click onto the grid, and break clicking a day to record it.
  - **The click that ends a mouse drag lands on the grid**, the common ancestor, because of the capture, and is ignored. The flag that ignores it is reset on the next press, since a touch drag fires no click.
  - **`touch-action: pan-y`** lets a vertical swipe scroll the page. The browser then sends `pointercancel`, which puts the range back.
  - **The Lifetime rows' FLIP** sets an inline `transition` for the slide and clears it on `transitionend`. Otherwise it would override the row's own opacity transition when the pick changes.
  - **Checking motion:** the Browser pane freezes transitions while it's hidden. These were checked by driving headless Edge over CDP, with real mouse, touch and key events and screenshots. In a phone emulation, a `captureBeyondViewport` screenshot shifts where the next touch lands, so take plain screenshots before touch steps.
- Every category page ships with an "add new" form for **both** its master/definition entity (a new Card, Account, Subscription, Loan, IncomeSource, FixedDeposit) **and** its log tab (a statement, a payment, an income entry) — not log tabs only. This is a firm requirement, not a nice-to-have: the explicit point of the app is that adding data never again requires opening the Sheet directly. Full inline editing of historical rows is still fine to land incrementally per page — that's about correcting existing data, a different (lower-priority) concern from being able to add new data at all.

## Secrets & auth

Already covered by [CLAUDE.md](../CLAUDE.md)'s Secrets Handling rule and [.gitignore](../.gitignore): the service account JSON key and Spreadsheet ID live in a local, gitignored `.env.local`, read only server-side. No OAuth, no login flow, no user-facing auth needed for a single-user local app. If hosting happens later, the same env vars move to that platform's secret store unchanged.

## Deployment

Deferred by design — v1 is `npm run dev` only (hosting is M2: #4, #17, #18, #19, and ADR 0007). Config is env-var driven, and the statement sync keeps its state in the Sheet since #82, but two things still assume this laptop:
- The Sheets service account key is read from a file path (`GOOGLE_SERVICE_ACCOUNT_KEY_FILE`). A host needs it from a secret setting holding the key itself.
- The scheduled sync is `scripts/ingestStatements.ts`, run by launchd against a running dev server. On Vercel it would be a Vercel Cron request to `/api/statements/sync`, which needs the login (#17) or a cron secret first.

## Phased implementation roadmap

1. **Foundation**: create the new Google Sheet with the tabs above as native Tables (except `Prices`, a plain range) including `InvestmentTransactions` and `Prices`; set up the Next.js project; wire the service account + `lib/sheets/client.ts`; implement one repository (`Accounts`) end-to-end as a proof of concept — this is also where we verify the Table-append-via-API risk noted above, early, before building on top of it.
2. **Read path for all entities**: remaining repositories (`Cards`, `Subscriptions`, `IncomeSources`, `Loans`, `InvestmentTransactions`) + their log tabs; `lib/aggregate/recurring.ts` and the per-entity aggregate modules (`accounts`, `cards`, `subscriptions`, `income`, `loans`, `investments`) for net worth, per-category totals, and investment positions.
3. **Overview page**: net worth summary (including investments), trend chart, stat tiles, Refresh button. **Built and verified in the browser, both empty and populated with real linked data** — net worth, monthly obligations, and the attention list all matched hand-checked math exactly (e.g. ₹2,10,000 bank − ₹12,500 card − ₹1,20,000 loan = ₹77,500 net worth; monthly obligations correctly excluded a loan installment not due until the following month).
   - **Scope decision**: true net-worth-over-time would require reconstructing loan/card/investment state at every past date, not just bank balances — real complexity, not just UI work. The trend chart instead shows bank-balance history (`lib/aggregate/accounts.ts`'s `balanceTrend`, real `BalanceSnapshot` data), while net worth itself is shown as a current point-in-time figure. Revisit if a true historical trend becomes worth the reconstruction cost.
   - **Real bug caught wiring the Refresh button**: calling the `updateTag`-based Server Action alone did nothing visible — it invalidates the cache, but the current page's already-rendered data doesn't re-fetch on its own. `RefreshButton` also calls `router.refresh()` after the action resolves; confirmed working in the browser (stale ₹0s → correct real numbers after one click).
4. **Category pages**: one at a time — Accounts, Cards, Subscriptions, Income, Loans, Investments (+ FixedDeposits) — each with its list/detail view, an "add" form for the master entity itself (new Card, new Loan, ...), and an "add" form for its log tab (new statement, new payment, ...). A page isn't done until both exist — that's what makes manual Sheet editing for adding data unnecessary going forward. Investments is where the `GOOGLEFINANCE` price/FX approach gets wired up and tested against real symbols.
5. **Polish**: upcoming-due-date alerts, styling pass, responsive check.

## Verification

- After any change to a tab or a repository, `npm run check-sheet` (with `npm run dev` running) confirms the two still match: names, order, column types and dropdown values. See "Verifying the Sheet".
- Each repository gets a quick manual check against the real (new) Sheet: create a row via the app, confirm it appears in Sheets *inside the Table range* with its dropdowns/column types intact (not as a plain row below the Table); edit a Sheet row directly, hit Refresh, confirm the app picks it up.
- `lib/aggregate` functions get unit tests against fixture data (no live Sheets calls needed) so net-worth math is verified independent of the data source.
- Before treating a page "done," load it in the browser (dev server) and check both a populated state and an empty/zero-data state (e.g. a category with no rows yet) render sensibly.
